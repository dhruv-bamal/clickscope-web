# Notes

## Phase 12a: Design System Integration

### Server Components vs. Client Components

**What it is.** Next.js's App Router renders every component as one of two kinds. A Server Component runs only on the server: it can be `async`, it can read files or query databases directly, and its output is serialized into the React Server Component (RSC) payload — a compact description of the tree, not JavaScript. A Client Component is marked with a `"use client"` directive at the top of its file; it hydrates in the browser, can hold state, and can attach real event listeners to DOM nodes. Every file in this project is a Server Component by default unless it opts into `"use client"`.

**Why it exists in this project.** Phase 12a's entire component-conversion pass (task 4 of the plan) hinges on getting this classification right for 25 exports across 24 files. Get it wrong in one direction and you ship a fully client-rendered app with no benefit from the App Router at all; get it wrong in the other and the build fails outright with an RSC boundary error. There is no partial credit — `npm run build` either succeeds or names the exact line that crossed a boundary it shouldn't have.

**How it works mechanically.** A Server Component categorically cannot: call a React hook (`useState`, `useEffect`, `useId`, `useContext` — none of them; the RSC renderer doesn't implement a hooks dispatcher for them), touch a browser-only API (`window`, `document`, `localStorage`), or attach a live event handler to a native DOM element in a way that survives serialization — a function value has no representation in the RSC payload, so `<button onClick={fn}>` rendered from a pure Server Component tree fails at build/render time with "Event handlers cannot be passed to Client Component props." What it *can* do that a Client Component can't: be `async` and `await` directly in the component body, which this phase uses for real — `QrCodePopover` and its inner `QrGlyph` are `async function` Server Components that `await QRCode.toString(shortUrl, { type: "svg" })` and stream the resulting SVG down as markup, with zero client JavaScript involved in generating it.

**Where it lives in the codebase.** The per-component classification is the table in the initial plan for this phase (25 exports; 5 need `"use client"`, 20 don't) and is re-derived, file by file, in `src/components/design-system/`. `src/components/design-system/feedback/QrCodePopover.tsx` is the concrete async-Server-Component example — and it's the reason `src/app/design-system/page.tsx` (the showcase) is *not* one big `"use client"` file despite being an internal dev-only page that would otherwise have no reason to split boundaries. It was written that way at first, and it broke immediately: React DevTools' console flagged `<QrCodePopover>` and its inner `<QrGlyph>` with "is an async Client Component. Only Server Components can be async at the moment," the instant the page tried to render QrCodePopover from inside a `"use client"` tree. The fix was the split now in place — `page.tsx` stays a Server Component and renders `<QrCodePopover>` directly, `src/app/design-system/ShowcaseInteractive.tsx` is the one `"use client"` boundary holding every other demo's state, and `src/app/design-system/Section.tsx` is a small hooks-free wrapper both files import. That's a stronger demonstration of "boundaries are contagious downward, not upward" than a clean build would have been: it's not just that the *other* 20 components don't need `"use client"` — it's that one of them (QrCodePopover) actively *cannot* tolerate being pulled into a client boundary it doesn't need, and the page has to be shaped around that.

**Common pitfalls.** Two, both actually hit by this phase, not hypothetical. First: `src/components/patterns/EditLinkModal.tsx` originally synced its local form state from `initialValues` inside a `useEffect` — a Client Component, so it compiled fine, but it's still wrong, and oxlint's `react/set-state-in-effect` rule caught it immediately (`npx oxlint --import-plugin src`). Calling `setState` synchronously inside an effect schedules a second, redundant render; the fix was to initialize state directly from props on mount and document a `key`-based remount contract for callers that need to reset the form when the target link changes, rather than reacting to a prop change after the fact. Second, the one described above: rendering an async Server Component from inside a `"use client"` tree fails at runtime, not build time — `npm run build` and `npm run lint` both passed cleanly with the bug in place; only opening the page in a browser and reading the console surfaced it, which is the concrete reason this phase's own plan called for using the feature in a browser rather than trusting the build alone.

**Production considerations.** The build is the enforcement mechanism, not a linter: get a boundary wrong and `npm run build` fails with a specific, named error rather than silently degrading. That's a stronger guarantee than most architectural conventions get, but it also means the failure mode is a full build break, not a warning — worth running `npm run build` after any component-library change, not just `npm run dev`, since dev mode is more forgiving about some boundary violations that only surface under production compilation.

**Interview answer.** Server Components run once on the server and serialize to a compact payload; they can't hold state, use hooks, or attach live event handlers, because none of that survives being flattened into a description of a tree. Client Components hydrate in the browser and can do all of that, at the cost of shipping JavaScript. Next.js defaults every file to a Server Component; you opt a file into the client with `"use client"` only when it actually needs interactivity. Getting the boundary wrong isn't a style nit — it's a build error, because a function handler or a hook call has no valid representation once it's serialized into the RSC payload.

### `"use client"` is a boundary, not a file marker — the Icon case

**What it is.** `"use client"` doesn't mean "this file uses React"; it means "this file is the seam where the client module graph begins." Everything that file imports and renders directly — every component in *its* module graph that doesn't have its own `"use client"` — gets pulled into the client JavaScript bundle too. But that pull only runs *downward*, into what the Client Component imports. It does not run *upward*, into whatever imports the Client Component. A Server Component can import and render a dozen different Client Components as children without becoming one itself, because each of those is a separate, self-contained boundary — the Server Component just describes where they go in the tree and hands them their props.

**Why it exists in this project.** Before this phase, `docs/design/components/icon/Icon.jsx` was the one component actively fighting this model: it used `useEffect` + `useRef` to imperatively inject `<i data-lucide="name">` into the DOM and then called the CDN global `window.lucide.createIcons()` to hydrate it into an SVG. Real hooks, a real browser-only global — Icon genuinely needed `"use client"`, no way around it. And Icon is imported by essentially every other component in the library (`Button`, `Badge`, `LinkCard`, `Toast`, `IconButton`, `EmptyState`, `StatCard`, `DataTable`'s cell renderers, and on) — it's the single most-imported module in the whole bundle. The naive, *wrong* conclusion from that fact is "Icon needs `use client`, so everything that renders `<Icon>` needs it too" — treating the directive as contagious upward. It isn't. A component that renders `<Icon name="copy" />` and has no hooks or browser APIs of its own stays a perfectly valid Server Component regardless of what Icon itself is; Icon becomes its own small client boundary nested inside an otherwise server-rendered tree, and the parent never needs the directive at all.

**How it works mechanically.** This phase rewrote `Icon.tsx` (`src/components/design-system/icon/Icon.tsx`) to resolve icon names through a static, eager `Record<string, LucideIcon>` map built from `lucide-react`'s named exports — no `useEffect`, no `useRef`, no CDN global, no hooks at all. That makes Icon itself a plain, pure, fully server-renderable function component. The real, measurable effect isn't that 20 *other* components stopped needing `"use client"` because of Icon — under the correct downward-only model, they never needed it on Icon's account in the first place. The effect is that the temptation to over-mark them evaporates, and each of the 25 exports in the library can be judged purely on *its own* hooks/browser-API usage, with no Icon-shaped asterisk. That per-component audit is what actually produced the count: 20 of 25 exports need nothing; the other 5 (`Modal`, `AnalyticsChart`, `Input`, `Textarea`, `Select`) need `"use client"` for reasons that have nothing to do with Icon — `Modal` for its own `useEffect`+`window.addEventListener` Escape-key handling, and `AnalyticsChart`/`Input`/`Textarea`/`Select` for their own `useId()` calls (a hook, and therefore just as unavailable to a Server Component as `useState` — this one is easy to miss, since `useId` doesn't *look* stateful the way `useState` does, but the RSC renderer doesn't special-case it).

**Where it lives in the codebase.** `src/components/design-system/icon/Icon.tsx` (the rewrite itself); the client/server classification table in this phase's plan lists all 25 exports with a one-line reason each; `src/components/design-system/feedback/Modal.tsx`, `src/components/design-system/data-display/AnalyticsChart.tsx`, and the three `forms/{Input,Textarea,Select}.tsx` files each carry a top-of-file comment naming their specific hook, not a generic "needs use client" note — the specificity matters, because it's what makes each classification independently verifiable rather than copied down a list.

**Common pitfalls.** Assuming `"use client"` propagates upward through the import graph — it doesn't, and designing a component library as if it does leads to marking dozens of presentational leaf components client-only for no reason, which quietly reintroduces the client-bundle bloat Server Components exist to avoid. The opposite mistake is just as real: components that merely *forward* an `onClick`/`onChange` prop via `{...rest}` (`Button`, `IconButton`, `Checkbox`, and others) don't need `"use client"` themselves — but the moment some ancestor actually attaches a real function to that prop, a client boundary needs to exist *somewhere* between the data-fetching Server Component and that DOM element. This phase ships no such wiring yet (no data fetching, no real handlers — that's 12b), so it's untested by this phase's own build; 12b is where a wrong assumption here would first surface as a real error.

**Production considerations.** Every additional `"use client"` boundary is JavaScript the browser has to download, parse, and hydrate. A design-system library that marks its leaf primitives client-only "just in case" pays that cost on every page that imports any of them, even pages that render those components in a fully static context. Keeping the boundary at the smallest possible unit — one hook-bearing component, not its entire subtree of importers — is a real, compounding performance decision, not a stylistic one.

**Interview answer.** `"use client"` marks a boundary, and boundaries only pull things in one direction: into the client bundle go the file itself and everything *it* imports and renders directly, but nothing upstream of it is affected. Icon originally needed the directive because it used `useEffect`, `useRef`, and a browser-only CDN global to inject SVGs imperatively; since it's imported by nearly every other component in the library, it would be easy to conclude the whole library needed to go client-side. That conclusion is wrong — a Server Component can render a Client Component as a child and stay a Server Component itself. Rewriting Icon to a static, hook-free lookup over `lucide-react` made Icon itself server-safe, which matters less for what it directly fixed and more for removing the reason anyone would've reached for the wrong mental model in the first place. The actual audit, done per-component and independent of Icon, found 5 of 25 exports need `"use client"` — each for a hook or browser API that's genuinely its own.

### Token architecture: plain CSS custom properties, not Tailwind

**What it is.** The design-system bundle ships its visual language as CSS custom properties — `--color-primary`, `--space-4`, `--radius-lg`, and so on — defined once in `tokens/*.css` and consumed via `var(--token-name)` everywhere, including inline `style={{ padding: "var(--space-4)" }}` objects throughout the reference screens. Every component class (`cs-btn`, `cs-card`, `cs-modal`, …) is hand-written BEM-like CSS in `css/components.css` that reads those same variables. This project ported that system into `src/styles/design-system/` unchanged in structure, imported once from `src/app/globals.css`.

**Why it exists in this project.** The bundle's own `uploads/design_v2.md` spec is written *as* a Tailwind v4 `@theme` document — but the actual shipped CSS in `docs/design/css/` and `docs/design/tokens/` doesn't use Tailwind at all. Grepping both files for `@tailwind`/`@apply` returns zero hits. That's not an oversight to correct; it's the real, load-bearing authoring convention of every file in the bundle, and every reference screen in `docs/design/ui_kits/` lays out with inline `style={{ ... }}` objects referencing the same custom properties rather than utility classes. Adding Tailwind to this project would mean introducing a second, parallel styling system with zero existing components to migrate onto it, a build-time cost, and a convention that matches nothing already here — pure overhead with no components it would actually simplify.

**How it works mechanically.** `src/styles/design-system/index.css` is a pure `@import` manifest (fonts → tokens → base → components, same order as the source bundle's `styles.css`), imported exactly once from `src/app/globals.css`, which `layout.tsx` imports exactly once. One deviation from the source, made deliberately: `tokens/fonts.css`'s Google Fonts CDN `@import` for Geist/Geist Mono was dropped in favor of `next/font/google`, which Next.js's own `create-next-app` scaffold already wires into `layout.tsx` — it self-hosts both font files at build time and exposes them as `--font-geist-sans`/`--font-geist-mono` on `<html>`. `tokens/typography.css`'s `--font-sans`/`--font-mono` now resolve those variables first, falling back to the literal family names. Same tokens, same visual result, one less external network dependency — and it resolves the second half of the bundle's own readme caveat ("Geist/Lucide loaded from CDN rather than vendored"), the Lucide half being what the Icon rewrite already fixed.

**Where it lives in the codebase.** `src/styles/design-system/tokens/{colors,typography,spacing}.css`, `src/styles/design-system/css/{base,components}.css`, `src/styles/design-system/index.css` (the manifest), `src/app/globals.css` (the one-line entry point), `src/app/layout.tsx` (the `next/font` wiring).

**Common pitfalls.** Reaching for a utility class that doesn't exist because there's no Tailwind config generating one — every visual value in this project comes from an explicit token or an inline `style` object, never a `p-4`/`bg-slate-100`-style class. The oxlint adherence config's raw-hex/raw-px/raw-font-family bans were meant to catch exactly the failure mode of someone hand-writing a value instead of reaching for a token — see the "what the bundle gave and didn't give" section below for why that specific enforcement mechanism doesn't currently run.

**Production considerations.** Because every component already consumes tokens via `var()` rather than any build-time class generation, there's no purge/JIT step to configure and no risk of a class being tree-shaken away because a linter didn't detect it in a dynamic string. The tradeoff is the inverse of Tailwind's: verbose inline `style` objects instead of terse utility classes, in exchange for zero build tooling and a token system that's just... CSS, legible without a mental compile step.

**Interview answer.** The source bundle's spec document describes a Tailwind v4 `@theme` design, but the CSS it actually ships is 100% hand-written custom properties consumed via `var()`, with zero Tailwind directives anywhere — confirmed by grep, not assumption. Every reference screen lays out with inline styles referencing those same variables. Given that, adding Tailwind to this project would mean running two styling systems side by side with nothing to migrate onto the new one — pure cost, no benefit. So this phase ported the token system as-is, with one real improvement: swapping the source's CDN-loaded Geist fonts for `next/font/google`, which Next.js already wires up, self-hosting the fonts and removing an external network dependency without changing a single visual token.

### Deriving view state from domain facts

**What it is.** `deriveLinkStatus()` (`src/lib/deriveLinkStatus.ts`) is one pure function that maps five independent domain booleans/values from the API's `Link` resource — `isActive`, `expiresAt`, `maxClicks`, `clickCount`, `isPasswordProtected` — onto the design system's single, mutually-exclusive `status` enum (`active | expiring | expired | protected | paused`) that `Badge` and `LinkCard` already expect.

**Why it exists in this project.** `clickscope-api` has no `status` field on `Link` at all — it was never a design goal there. What it does have, in `src/routes/redirect.ts`'s `deadStateError()`, is a priority-ordered check for whether a link is *dead*: inactive wins first, then a past `expiresAt`, then an exhausted `maxClicks`, all three collapsing to the same 410 Gone response. That function exists for a redirect handler's narrow purpose (should this request be served or not) and was never meant to produce a five-value UI enum. The frontend needs its own mapping, but it needs to encode the *same underlying precedence logic* the API already committed to, or the two would silently disagree about what "dead" means. The trickiest fact this function has to get right, and the reason it can't just read `isActive` naively: `worker/processors/linkCleanupProcessor.ts`'s scheduled sweep only flips `is_active = false` for links dead by *expiry* — never for links dead by exhausted `maxClicks` — and it runs on a delay. So a click-capped link can sit with `isActive: true` in the database indefinitely, and a time-expired link can sit with `isActive: true` for a window after it expires but before the sweep runs. Reading `isActive` at face value would show "Active" for links that are, functionally, already dead.

**How it works mechanically.** Five ordered rules, most severe first: (1) `expired` if `expiresAt` has passed *or* `clickCount >= maxClicks` — checked before `isActive`, specifically so an unswept, click-capped-or-past-expiry link shows "Expired" rather than the misleading "Active"; (2) `paused` if `isActive` is false and rule 1 didn't already fire — this is what correctly isolates a genuine manual deactivation from an unswept natural expiry, since the expiry/cap check already ran first; (3) `protected` if `isPasswordProtected` and the link isn't within the expiring-soon window; (4) `expiring` if `expiresAt` is within 3 days — chosen as the threshold on the reasoning that it's wide enough to be useful without being so early it becomes noise, and it wins over `protected` when both are true, since time pressure is actionable in a way a static password setting isn't; (5) `active` otherwise. All three of these — the 3-day window, click-cap counting as expired, and expiring-over-protected precedence — are product decisions with no single objectively correct answer; they were made explicitly rather than defaulted into silently, which is the entire point of writing them down here instead of letting them fall out of whichever screen happened to need a status first.

**Where it lives in the codebase.** `src/lib/deriveLinkStatus.ts` (the function and its inline precedence comments); `src/types/link.ts` (the hand-written `Link` interface it types against — hand-written because `clickscope-api` and `clickscope-web` share no types package or OpenAPI spec, so this is the one place that shape gets asserted on the frontend and has to be kept in sync by hand); `clickscope-api/src/routes/redirect.ts`'s `deadStateError()` and `clickscope-api/worker/processors/linkCleanupProcessor.ts`'s `sweepExpiredLinks` (the API-side precedent this function's ordering is built to stay consistent with).

**Common pitfalls.** Computing status inline in a component from `link.isActive ? "active" : "paused"` — the single most tempting shortcut, and exactly what produces the "unswept link shows Active" bug described above. Anywhere this function's logic gets duplicated instead of imported, the list view and the detail view are one edge case away from disagreeing about the same link's status, and neither call site would have any signal that they'd drifted.

**Production considerations.** One function is the whole point here, not a stylistic preference: every consumer — the link list, the detail header, a future email digest or Slack notification — must apply identical precedence, and a single source of truth is the only way a future change to, say, the expiring-soon window doesn't require hunting down every place that logic got copied.

**Interview answer.** The API has no `status` field — it has five independent facts, and its own redirect handler already estabishes a priority order for treating a link as dead (inactive, then expired, then click-capped) for its own narrow purpose. `deriveLinkStatus()` is one pure function that reuses that same precedence to produce the UI's single status enum, and it specifically checks expiry and click-cap *before* `isActive`, because the API's cleanup worker only sweeps expired links on a delay and never sweeps click-capped ones at all — so a dead link can sit with `isActive: true` for a while, and reading that flag naively would show it as live. Three product decisions (the 3-day expiring window, click-cap counting as expired, and expiring beating protected when both are true) got made explicitly and surfaced rather than picked silently, and it's one function specifically so every screen that shows a status agrees with every other one.

### What the handoff bundle gave and didn't give

**What it is.** `docs/design/` is a complete, internally consistent design-system handoff: CSS tokens, a Geist type system, 24 React components each with a paired `.jsx` implementation, `.d.ts` prop contract, and `.prompt.md` usage doc, four full-screen reference UI kits, and an oxlint "adherence" config meant to enforce the whole thing at lint time. Its own readme calls it "complete and validated," with two caveats: no real logo, and Geist/Lucide loaded from CDN rather than vendored.

**Why it exists in this project.** Knowing precisely where the bundle's authority ends matters more than restating what it covers well — everything past that line is a decision this phase had to make (and in several cases, explicitly ask about) rather than one the bundle made for it.

**How it works mechanically — what it gave.** All 24 components port cleanly with their `.d.ts` folded in as real TypeScript interfaces (`src/components/design-system/`). The token system, base reset, and component CSS are complete enough to need zero new visual decisions for anything the bundle already modeled. `Modal.prompt.md` documents the destructive-confirm pattern precisely enough that `DeleteConfirmModal` (`src/components/patterns/DeleteConfirmModal.tsx`) is a direct instantiation of it, not an invention. The reference `SignInScreen`/`AuthCard` layout in `docs/design/ui_kits/` was faithful enough to mirror exactly for the new `SignupForm` (`src/components/patterns/SignupForm.tsx`) — centered card, icon-in-circle header, OAuth button + divider, `cs-card` body — with no new layout invented, just new fields.

**What it didn't give.** No `package.json`, no `lucide-react` (Icon was CDN-only — the rewrite this phase's whole first half is built around). No pagination component or pattern anywhere, despite the API's `GET /api/links` returning exactly the offset/limit/total/hasMore shape a Prev/Next control needs (`src/components/patterns/Pagination.tsx` is new). No signup screen — only a dead `href="#"` stub inside the reference `SignInScreen`, and no `name` field to collect even if there were, since `clickscope-api`'s `users` table has none (`migrations/20260810111606772_create-users-table.ts`). No `max-clicks` input anywhere, in *any* form, despite the API fully supporting the field — `EditLinkModal` adds one as a plain `Input`, matching the user's explicit call on that gap. A `QrCodePopover` whose glyph is explicitly commented `/* Deterministic visual QR glyph (NOT scannable) */` — replaced with `qrcode`'s real SVG renderer, `await`-ed inside an async Server Component. A `Tag` component and an ad-hoc tags column in the reference `LinksScreen`, for a field (`tags`) that doesn't exist anywhere in the API's schema — confirmed via a repo-wide grep, zero hits — so nothing in this phase's ported components or new patterns wires a tags field to anything. And an oxlint adherence config written against ESLint's `no-restricted-syntax` rule, which the installed oxlint version (1.79) doesn't implement at all — `oxlint -c _adherence.oxlintrc.json` fails outright with "Rule 'no-restricted-syntax' not found in plugin 'eslint'." Its `no-restricted-imports` half works and was kept (with the path globs fixed to this project's real `@/components/design-system/*/**` alias); its 41 per-component prop-contract selectors were dropped rather than resurrected, both because they can't run under this oxlint version and because — even setting that aside — they'd be redundant with TypeScript now that every component is a real `.tsx` file with a real interface, and actively wrong for the six components (`Button`, `IconButton`, `Input`, `Textarea`, `Select`, `Checkbox`) that spread `{...rest}` onto a native element and extend React's own `*HTMLAttributes<...>`: the generated allowlists only included each component's own custom props, so they'd have flagged ordinary, correct usage like `<Input type="email" onChange={...} />` as a violation. Full reasoning in `.oxlintrc.json`'s header comment.

**Where it lives in the codebase.** Everything above traces to a specific file already named in this section — that specificity is deliberate, so this note stays checkable against the code rather than becoming stale prose.

**Common pitfalls.** Assuming "complete and validated" in the bundle's own readme means complete for *this* product — it means complete relative to the visual spec it was built against, which never modeled auth screens, pagination, or a max-clicks input in the first place, and separately never got test-run against the actual lint tool this project uses. Both are worth checking explicitly rather than inheriting the bundle's own confidence in itself.

**Production considerations.** None of this phase's four new patterns (`SignupForm`, `DeleteConfirmModal`, `EditLinkModal`, `Pagination`) or the QR/oxlint fixes required inventing new visual language — every one of them composes existing tokens and existing components, or (for oxlint) removes rules that can't run rather than replacing them with something new. That constraint held throughout specifically so 12b's API-wiring work inherits a design surface with zero pending "which one is real" ambiguity.

**Interview answer.** The bundle is genuinely complete for what it set out to model — tokens, 24 components, four reference screens — but "complete" has a boundary, and this phase's job was finding it precisely rather than assuming it. Concretely: no npm dependencies at all (Icon's CDN dependency was the big one), no pagination, no signup screen, no max-clicks input despite the API supporting the field, a QR code that explicitly isn't scannable, a `Tag` component built for a field the API schema doesn't have, and an adherence lint config written against a rule (`no-restricted-syntax`) the actual installed linter doesn't implement. Every gap got a specific fix traced to a specific file, and every new piece reused existing components and tokens rather than inventing new ones — the four new patterns and the QR/oxlint fixes are compositions of what already existed, not new design decisions.

## Phase 12b: API Integration

### The one API client, and the typed error it never lets you skip

**What it is.** `src/lib/api.ts` is the only file in the project that reads `NEXT_PUBLIC_API_URL` or constructs a request to `clickscope-api`. Every call — `signup`, `login`, `getMe`, `createLink`, `listLinks`, `getLink`, `getLinkStats`, `updateLink`, `deleteLink` — funnels through one internal `request<T>()` that attaches `Authorization: Bearer <token>` when a token is passed, and throws a typed `ApiError` (carrying `status`, `code`, `requestId`, `details`, and — only on a 429 — `retryAfterSeconds`) on any non-2xx response.

**Why it exists in this project.** Without a single choke point, every call site would independently decide how to build the URL, whether to attach the header, and how to parse `{ error: { code, message, requestId } }` — and the header-attachment step is exactly the kind of thing that's trivial to forget once in fifteen call sites and then spend an hour debugging a 401 that only reproduces on one screen.

**How it works mechanically.** Two response shapes need special-casing before the generic JSON path runs. First, `DELETE /api/links/:id` returns `204 No Content` — calling `.json()` on an empty body throws a `SyntaxError` ("Unexpected end of JSON input"), not a usable error, so `request<T>()` checks `res.status === 204` and returns `undefined as T` before ever calling `.json()`. Second, a `429` gets its own branch: the retry delay can come from the body's `details.retryAfterSeconds` or the `Retry-After` header, and `ApiError.retryAfterSeconds` normalizes both into one field so a caller never re-parses either.

**Where it lives in the codebase.** `src/lib/api.ts` (the client and `ApiError` class), `src/types/api.ts` (every request/response/error shape it's typed against), every call site in `src/context/AuthContext.tsx`, `src/components/patterns/{LoginForm,SignupForm,CreateLinkModal}.tsx`, and `src/app/dashboard/DashboardInteractive.tsx`.

**Common pitfalls.** Calling `.json()` unconditionally on a `DELETE` response — this genuinely would have broken the delete flow's happy path, not just its error path, since a 204's body is empty by definition, not malformed JSON.

**Interview answer.** One file owns the base URL, the auth header, and error parsing, so every one of the nine API calls in this app behaves identically on the two failure modes that are easy to get wrong per-call-site: a 204 with no body, and a 429 whose retry delay can live in two different places (a header or the body). Centralizing it means those two edge cases get handled once, correctly, instead of being re-discovered (or missed) at each call site.

### `NEXT_PUBLIC_` is a security boundary, not a naming convention

**What it is.** Next.js inlines any env var prefixed `NEXT_PUBLIC_` into the client JavaScript bundle at build time — it becomes a literal string baked into shipped code, readable by anyone who views source. An *un*-prefixed var is only available in Server Components, Route Handlers, and other server-only code; reading it from a Client Component doesn't fail to build — it silently returns `undefined` at runtime.

**Why it exists in this project.** `NEXT_PUBLIC_API_URL` genuinely has no secret in it — it's a base URL, not a credential — so exposing it to the browser is correct. But the prefix isn't decorative: it's the literal mechanism that makes the value reach `src/lib/api.ts`, which runs entirely client-side (see the "server vs. client fetching" entry below). Get the prefix wrong — omit it, or typo it — and the failure mode isn't a build error. `BASE_URL` becomes `undefined`, `fetch(\`${undefined}/api/...\`)` resolves to a relative URL like `/api/auth/login` evaluated against the Next.js dev server's own origin, and that 404s against Next's own (nonexistent) route instead of clickscope-api — a confusing "why is my JSON API returning an HTML 404 page" bug, not a clear "env var missing" one. `src/lib/api.ts` `console.error`s loudly in the browser if `BASE_URL` is falsy specifically to shortcut that debugging session.

**Where it lives in the codebase.** `.env.local.example` (the var itself, with this reasoning in a comment), `src/lib/api.ts`'s `BASE_URL` constant and its guard.

**Common pitfalls.** Assuming an unprefixed var "just doesn't get inlined" the way a bundler's dead-code elimination silently drops something — it's not dropped, it's a real runtime `undefined`, which is worse: no build warning, no obvious signal, just a value that looks present in `.env.local` but was never actually delivered to the code reading it.

**Interview answer.** `NEXT_PUBLIC_` isn't a style convention, it's the actual boundary between "safe to expose to a browser" and "server secret" — Next.js literally inlines prefixed vars into the client bundle at build time and leaves unprefixed ones server-only. Using it correctly here is easy (the API base URL has no secret in it), but the failure mode if you forget it is worth knowing: no build error, just `undefined` silently reaching a client component, turning into a relative-URL fetch against the wrong origin, and 404ing in a way that looks like a backend problem instead of a config one.

### The provider pattern: `providers.tsx` between a Server `layout.tsx` and `AuthContext`

**What it is.** `src/context/AuthContext.tsx` is a `"use client"` file exporting `AuthProvider` and a `useAuth()` hook. `src/app/providers.tsx` is a thin `"use client"` wrapper — today just `<AuthProvider>{children}</AuthProvider>` — imported into `src/app/layout.tsx`, which itself carries no `"use client"` directive and stays a Server Component.

**Why it exists in this project.** React context has no representation in the RSC payload — it's a runtime mechanism tied to a component tree that hydrates in the browser, so `createContext`/`useContext` simply cannot run in a Server Component. That forces `AuthProvider` itself to be client-side. The interesting decision is where the `"use client"` boundary starts: not on `layout.tsx` directly, but on a separate `providers.tsx` file that `layout.tsx` imports and renders as a child. This is the same downward-only boundary rule 12a's Icon section already established (`"use client" is a boundary, not a file marker`) — a Server Component can render a Client Component as a child without becoming one itself.

**How it works mechanically.** If `"use client"` were put directly on `layout.tsx` instead, every route in the app would be pulled inside that boundary — including `/design-system`, which 12a's Notes.md already documents as deliberately kept server-rendered specifically so `QrCodePopover` (an `async function` Server Component) can be rendered directly from `page.tsx`. `QrCodePopover` cannot be rendered from inside a `"use client"` ancestor at all — React throws "Only Server Components can be async" at runtime, the exact bug 12a already hit and documented, caught only by opening the page in a browser, not by `npm run build`/`npm run lint`. A `"use client"` root layout wouldn't just cost bundle size across the whole app — it would break `/design-system` outright, the same class of failure 12a already diagnosed once at smaller scale. Keeping `layout.tsx` a Server Component and pushing `"use client"` down into `providers.tsx` is what keeps that page working at all in this phase. (Confirmed, not just reasoned about: `npm run build` after wiring this up prerendered `/design-system` as static alongside every new route — see "production considerations" below.)

**Where it lives in the codebase.** `src/context/AuthContext.tsx`, `src/app/providers.tsx`, `src/app/layout.tsx` (the two-line edit: import `Providers`, wrap `{children}`).

**Common pitfalls.** Importing `AuthProvider` directly into `layout.tsx` and marking `layout.tsx` itself `"use client"` "since it needs the provider anyway" — the thin wrapper file is what avoids that; it's boilerplate today (one provider, no logic of its own) but it's the only thing standing between a two-line layout change and a whole-app client boundary.

**Production considerations.** 12a's own Notes.md already states the rule this phase leans on: "worth running `npm run build` after any component-library change, not just `npm run dev`, since dev mode is more forgiving about some boundary violations that only surface under production compilation." This phase followed that explicitly — `npm run build` was run (not just `next dev`) after wiring `providers.tsx`/`AuthContext`/`DashboardInteractive`/`LoginForm`/`CreateLinkModal`, and it's what actually confirms the boundaries are correct, not just that the dev server didn't complain.

**Interview answer.** Context can't exist in a Server Component, so `AuthProvider` has to be `"use client"` — but *where* that boundary starts matters. Putting it on a separate `providers.tsx` file, imported into a `layout.tsx` that stays a Server Component, means only that one small file and its subtree go client-side, not the entire app. Get this wrong — mark `layout.tsx` itself client — and you don't just ship more JavaScript than necessary, you break `/design-system`, which depends on `layout.tsx`'s children staying server-renderable so an async Server Component further down the tree can exist at all.

### The OAuth fragment redirect, and why `AuthContext` catches it instead of a route

**What it is.** `clickscope-api`'s `GET /api/auth/google/callback` finishes the OAuth exchange server-side and redirects the browser to `` `${FRONTEND_URL}#token=${token}` `` on success, or `` `${FRONTEND_URL}?error=oauth_denied` `` if the user denies consent. `AuthContext`'s mount-time effect checks `window.location.hash` for `#token=`, and if present, stores the token and calls `window.history.replaceState(null, "", pathname + search)` to remove it from the URL immediately.

**Why it exists in this project.** The token goes in the URL **fragment**, not a query parameter, because a fragment is never sent by the browser to any server — not clickscope-api, not a CDN, not a proxy in between — so it can't leak into access logs or a `Referer` header the way a query string would. The frontend has to read it from `window.location.hash` specifically because that's the one place a fragment is visible: client-side JavaScript, after the redirect has already landed.

**How it works mechanically.** `clickscope-api`'s `.env` has `FRONTEND_URL=http://localhost:5173` with **no path segment** — confirmed by reading the config directly, not assumed. That means the redirect always lands the browser at the frontend's root (`/`), whichever page that resolves to, regardless of which page the user started the OAuth flow from. Since clickscope-api can't be modified to redirect anywhere else, a dedicated `/auth/callback` route would simply never be hit by this redirect. `AuthProvider` is the only piece of frontend code guaranteed to mount on every route including root — so it's the only place that can reliably catch the fragment, and that's why the check lives in `AuthContext.tsx`'s mount effect rather than a page component.

**Common pitfalls.** Assuming "the fragment never reaches a server" means scrubbing it is optional — it isn't. The fragment is still visible in the browser's own history (a forward/back navigation replays it), in a screen share, and to any other script already running on the page via `location.href`; `history.replaceState` removes it from the current entry without adding a new one, a navigation, or a reload, closing all three of those residual exposures even though none of them involve a server at all.

**Where it lives in the codebase.** `src/context/AuthContext.tsx`'s first `useEffect` (the fragment-then-localStorage restore); `clickscope-api/src/routes/auth.ts`'s `/google/callback` handler (the redirect this responds to, confirmed by reading it directly — do not modify this file, it's out of scope for clickscope-web).

**Interview answer.** clickscope-api puts the OAuth token in a URL fragment specifically because fragments never reach a server, closing off access-log and Referer-header leakage. The frontend reads it from `window.location.hash`. The twist in this app: the API's `FRONTEND_URL` has no path, so the redirect always lands at the root, no matter which page the user started from — which means a dedicated callback route would never actually be hit, and the fragment check has to live somewhere guaranteed to mount on every route: the auth provider itself. And scrubbing the fragment with `history.replaceState` still matters afterward even though it never touched a server, because it's still sitting in browser history and readable by any other script on the page until it's removed.

### The localStorage XSS tradeoff, as a deliberate Phase 0 decision

**What it is.** The JWT issued by `/signup`, `/login`, and the OAuth callback is stored in `localStorage` (`src/context/AuthContext.tsx`), not an `httpOnly` cookie.

**Why it exists in this project.** `localStorage` is readable by any script that executes in the page's origin — a compromised dependency, a reflected XSS bug anywhere in the app — in a way an `httpOnly` cookie categorically is not, since JavaScript can't read those at all. This project accepts that tradeoff because there was no alternative available given two facts confirmed directly from clickscope-api's source: every token-bearing response (`/signup`, `/login`, the OAuth redirect) puts the token in a JSON body or a URL fragment, never a `Set-Cookie` header, and clickscope-api can't be modified to add one (out of scope for this phase). Given that starting point, `localStorage` is the only storage a `fetch().then()` handler and a `window.location.hash` read can both populate from client-side code.

**Where it lives in the codebase.** `src/context/AuthContext.tsx` (`localStorage.setItem`/`getItem`/`removeItem` calls).

**Interview answer.** The token lives in `localStorage` instead of an `httpOnly` cookie, which trades away some XSS resistance for something clickscope-api simply doesn't offer: every token-bearing response is a JSON body or a fragment, never a `Set-Cookie` header. Given that the API can't be changed in this phase, `localStorage` is the only storage both a `fetch` response handler and a fragment read can populate — an `httpOnly` cookie would need the API to set it, which isn't on the table here.

### Client-side route guards are UX, not security

**What it is.** `DashboardInteractive` redirects to `/login` when `!isLoading && !token`; `LoginForm` and `SignupForm` redirect to `/dashboard` when a session is already restored. All three checks live entirely in client-side React state.

**Why it exists in this project.** These guards exist purely to avoid flashing a broken or contradictory UI — a logged-out user briefly seeing an empty dashboard shell, or a logged-in user seeing a login form they don't need. They provide zero actual access control: a user with dev tools open can trivially skip past any of them, and the dashboard route would still render its shell underneath.

**How it works mechanically.** The real authorization boundary is entirely on the API side — `clickscope-api`'s `requireAuth` middleware rejects any `/api/links*` request without a valid `Authorization: Bearer` header, independent of anything the frontend renders. If a client-side guard were bypassed or simply absent, the dashboard would render its shell, its data-fetching effect would fire, and `GET /api/links` would 401 — surfaced as this app's own error-toast path, not a security failure, because no real data was ever at risk.

**Where it lives in the codebase.** `src/app/dashboard/DashboardInteractive.tsx`'s first `useEffect` and its `if (!isLoading && !token)` early-return `PageError`; the mirrored checks in `src/components/patterns/LoginForm.tsx` and `SignupForm.tsx`.

**Common pitfalls.** Redirecting on `!token` alone, without gating on `isLoading` — `AuthContext`'s mount-time restore is asynchronous (it has to read `localStorage` or a fragment, then resolve `/me`), so a real logged-in user would see `token === null` for one render before restore finishes, and an ungated guard would bounce them to `/login` on every page load before catching up.

**Interview answer.** These are convenience redirects, not a security layer — real authorization is entirely the API's job, enforced by its `requireAuth` middleware on every links request. The frontend guards exist only so the UI doesn't visibly contradict itself (a dashboard for a logged-out user, a login form for a logged-in one); if you deleted them entirely, the worst that happens is a flash of the wrong screen before a 401 error surfaces, never a data leak.

### Why every data-effect is keyed on `[token]`, never `[]`

**What it is.** Every fetch-triggering `useEffect` in this phase — `AuthContext`'s `/me` resolution, `DashboardInteractive`'s link-list fetch, `LinkStatsModal`'s stats fetch — lists `token` (plus any other primitive the fetch depends on, like `offset` or `days`) in its dependency array.

**Why it exists in this project.** The concrete bug an empty array causes: user A logs in, the dashboard's fetch effect runs once with `[]`, and fetches A's links. User A logs out and user B logs in — a different token — in the same tab session, no full page reload. Because the dependency array is `[]`, React never re-runs the effect on its own; nothing about a state change alone re-triggers an effect whose deps say "never re-run." The dashboard keeps rendering user A's stale link list under user B's session until something else forces a refetch. Keying on `[token]` makes the effect re-run the instant `token` changes to B's value, refetching automatically under the new identity — no manual "refresh on login" call needed anywhere.

**How it works mechanically.** React compares each entry in the dependency array between renders using `Object.is` (see the next entry for what goes wrong when an entry isn't a primitive); when any entry differs, the effect's cleanup runs, then the effect body runs again with the new values in its closure.

**Where it lives in the codebase.** `src/context/AuthContext.tsx`'s second `useEffect` (`[token]`), `src/app/dashboard/DashboardInteractive.tsx`'s link-list effect (`[token, offset]`), `src/app/dashboard/DashboardInteractive.tsx`'s `LinkStatsModal`'s effect (`[token, link.id, days]`).

**Interview answer.** An empty dependency array means "run once, on mount, and never again" — which is wrong for anything whose correctness depends on a value that can legitimately change during the component's lifetime, like which user is logged in. Keying the effect on `[token]` means a login, logout, or OAuth capture that changes `token` automatically re-runs the fetch under the new identity; without it, switching accounts in the same tab would silently keep showing the previous user's data until an unrelated re-render happened to also trigger a refetch some other way.

### AbortController cleanup and the stale-response race

**What it is.** Every fetch effect in this phase creates an `AbortController`, passes `controller.signal` into the `lib/api.ts` call, and returns `() => controller.abort()` as the effect's cleanup function.

**Why it exists in this project.** Concrete timeline: (t0) the dashboard's fetch effect runs with `offset=0`, firing `listLinks(..., offset: 0)`. (t1) before that resolves, the user clicks Next; `offset` becomes `20`, and because the effect is keyed on `[token, offset]`, React re-runs it — firing a second `listLinks(..., offset: 20)` — and, critically, first calls the *cleanup* from the first effect instance, which aborts the first (offset=0) request. (t2) Without that abort: if the network happens to resolve the first (offset=0) response *after* the second (offset=20) one — a slower connection, a GC pause, anything — its `.then()` would call `setLinks` with page-1 data *after* page-2 data has already rendered, silently reverting the UI to the wrong page with no visible error and no obvious cause to whoever's debugging it later. With the abort in place, the first request's promise rejects with a `DOMException` named `"AbortError"` before it can reach `setLinks` at all, and every `.catch()` in this codebase checks `err.name === "AbortError"` and returns early — treating it as an intentional cancellation, not a failure, so it never sets an error state either.

**Where it lives in the codebase.** Every fetch effect: `src/context/AuthContext.tsx`'s `/me` resolution, `src/app/dashboard/DashboardInteractive.tsx`'s link-list fetch, `src/app/dashboard/DashboardInteractive.tsx`'s `LinkStatsModal`'s stats fetch. `src/lib/api.ts`'s `request<T>()` accepts and forwards `signal` on every exported function specifically so every call site can do this.

**Common pitfalls.** Checking `err instanceof ApiError` before checking `err.name === "AbortError"` — an aborted `fetch()` rejects with a `DOMException`, not an `ApiError`, so an abort check has to come first or it falls through to whatever the generic error path does (in this codebase, that would incorrectly show an error toast for a cancellation the user caused on purpose by clicking Next).

**Interview answer.** Without cleanup, a fast dependency change (clicking Next before the previous page finished loading) can let an older, now-irrelevant request's response arrive *after* a newer one and silently overwrite it — the UI ends up showing stale data with zero error and zero indication anything went wrong. `AbortController` cancels the outdated request when its effect instance's cleanup runs, turning that race into a clean "ignore this, it was superseded" instead of a silent data-correctness bug.

### Controlled inputs: what breaks with `value` and no `onChange`

**What it is.** Every text/select/toggle field this phase adds or wires — `LoginForm`'s email/password, `CreateLinkModal`'s every field, `SignupForm`'s newly-added email field — pairs a `value` prop with an `onChange` handler that calls `setState`.

**Why it exists in this project.** 12a's `Input`/`Select`/`Textarea` already require both via their inherited `*HTMLAttributes` types, but that's a type looseness, not an enforcement — React itself only warns, it doesn't error, if you pass `value` without `onChange`. What actually happens: React logs a console warning ("You provided a `value` prop to a form field without an `onChange` handler...") and the field becomes read-only from the user's perspective — every keystroke fires a native input event, but since nothing calls `setState`, the component re-renders with the exact same `value` it started with, so nothing the user types ever visibly appears. It looks like a broken, frozen input, not an error.

**Where it lives in the codebase.** Every new/edited field in `src/components/patterns/{LoginForm,SignupForm,CreateLinkModal}.tsx` and `src/app/dashboard/DashboardInteractive.tsx`'s `LinkStatsModal` (`SegmentedControl`'s `value`/`onChange`, non-native but the same pairing requirement).

**Interview answer.** A controlled input's displayed value comes entirely from the `value` prop, not from what the browser's native input element would otherwise track internally — so without an `onChange` that feeds keystrokes back into state, the field is permanently locked to whatever `value` was initially, and every keystroke is silently discarded from the user's point of view. React warns about this in the console, but it's not a build error, so it's the kind of bug that would only get caught by actually typing into the form once.

### The Object.is dependency-array trap

**What it is.** React's `useEffect` dependency comparison uses `Object.is` — the same algorithm behind `===`, with two edge-case differences (`NaN` equals `NaN`, `+0` doesn't equal `-0`) that don't matter here. For objects and arrays, that means reference equality: two objects with identical contents are never `Object.is`-equal unless they're the literal same reference.

**Why it exists in this project.** The dashboard's link-list fetch needs both `limit` and `offset` as effect inputs. The naive way to pass them — `useEffect(() => {...}, [{ limit: 20, offset }])` — creates a brand-new object literal on every single render, since `{ limit: 20, offset }` is a fresh allocation every time that line executes, regardless of whether `offset`'s value actually changed. That new object is never `Object.is`-equal to the previous render's object, even when nothing meaningful changed, so the effect would re-run on *every* render — silently defeating the entire purpose of having a dependency array in the first place, and in this specific case, re-firing `listLinks` far more often than the offset actually changes.

**How it works mechanically.** This phase avoids the trap by destructuring primitives directly into the array: `[token, offset]`, never a wrapping object or array. `listLinks(token, { limit: LIMIT, offset }, ...)` still constructs an object, but that object is the function-call argument, not a dependency-array entry — its identity doesn't affect when the effect re-runs, only `token` and `offset`'s primitive values do.

**Where it lives in the codebase.** `src/app/dashboard/DashboardInteractive.tsx`'s link-list effect (`[token, offset]`) and `LinkStatsModal`'s stats effect (`[token, link.id, days]`) — both destructure every dependency into a primitive rather than passing a params object.

**Interview answer.** `useEffect`'s dependency check is reference equality for anything non-primitive, so a freshly-allocated object or array in the dependency array — even one built from values that didn't change — is never equal to last render's version, and the effect re-runs every render regardless. The fix is always the same: pass the primitive values themselves as separate array entries, never a wrapping object literal, so the comparison actually reflects "did the underlying value change" instead of "did I allocate a new object this render," which is true unconditionally.

### Server vs. client fetching was forced, not chosen

**What it is.** Every authenticated API call in this app — the dashboard's link list, stats, every mutation — happens inside a `"use client"` component, using `useEffect` and the plain `fetch`-based client in `src/lib/api.ts`.

**Why it exists in this project.** The token lives in `localStorage`. Server Components render on the server, where `window`/`localStorage` don't exist at all — a Server Component has no mechanism to read the token, so it categorically cannot make an authenticated request to clickscope-api on the user's behalf. Given the Phase 0 decision to store the token in `localStorage` rather than an `httpOnly` cookie (see that entry above), there is no server-side alternative available; this isn't a stylistic preference for client-side data fetching, it's the only option the auth storage choice leaves open. If the token instead lived in an `httpOnly` cookie set by clickscope-api on `/login`/`/signup` (which it does not currently do — out of scope to add here), the browser would attach it automatically to same-origin requests, a Next.js Server Component *could* read it via `cookies()` and fetch server-side, and most of `AuthContext`'s client-side restore logic — the mount-time `localStorage` read specifically, though the OAuth fragment capture would likely still need to happen somewhere client-side — would become unnecessary.

**How it works mechanically — and a disagreement worth surfacing, not eliding.** This repo's own bundled Next.js 16.3.1 docs (`node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md` and `01-app/02-guides/single-page-applications.md`) recommend React's `use()` API plus `<Suspense>`, or a library like SWR/React Query, for client-side fetching in Client Components — not raw `useEffect`. This phase uses `useEffect` anyway, deliberately: the goal here was to make the dependency-array/cleanup/stale-response mechanics visible and explainable at each call site, and `use()`+Suspense and SWR/React Query both exist specifically to abstract those mechanics away from the caller. This is a known, intentional departure from the current docs' recommendation, not an oversight — a later phase migrating this fetching layer to SWR or React Query once the teaching goal is no longer the point is a reasonable next step, and it should reuse `src/lib/api.ts`'s functions as the fetcher, since that file's job (base URL, auth header, error parsing) doesn't change regardless of what calls it.

**Where it lives in the codebase.** `src/lib/api.ts` (no `"use client"` itself, but every real caller is client-side), `src/context/AuthContext.tsx`, `src/app/dashboard/DashboardInteractive.tsx`.

**Interview answer.** Client-side fetching wasn't chosen for this app, it was forced by an earlier decision: the JWT lives in `localStorage`, which a Server Component simply cannot read, so no Server Component in this app can attach the auth header a real request needs. If the token lived in an `httpOnly` cookie instead, Server Components could read it via `cookies()` and fetch server-side — but that requires the API to issue the cookie, which clickscope-api doesn't do today. Separately: this repo's own Next.js docs actually recommend `use()`/Suspense or SWR/React Query over raw `useEffect` for client fetching, and this phase uses `useEffect` anyway on purpose, because the point here was making the dependency-array and cleanup mechanics visible rather than abstracting them away — a disagreement with the docs' recommendation, not a mistake.

### Surfacing `requestId` through `Toast.detail` without modifying `Toast`

**What it is.** Every mutation's caught `ApiError` renders a `Toast` whose `detail` prop is composed as the error's `message` plus a small muted `ref: {requestId}` line, via `src/app/dashboard/DashboardInteractive.tsx`'s `errorToast()` helper.

**Why it exists in this project.** `Toast` (`src/components/design-system/feedback/Toast.tsx`) has no dedicated `requestId` field — it never needed one before this phase, and adding one would mean editing a 12a design-system primitive for a single call site's need, which the ported design system explicitly wasn't meant to require. `detail` is already typed `React.ReactNode`, though, which means it accepts arbitrary composed content, not just a string — so embedding the requestId as a second line inside `detail` satisfies "surface the API's message and requestId" without touching `Toast.tsx` at all.

**How it works mechanically.** `errorToast()` also branches on `err.code === "TOO_MANY_REQUESTS"` before the generic path, producing a distinct `title: "Slow down"` and a `detail` built from `err.retryAfterSeconds` ("Try again in Ns") — a 429 gets a message about retrying, not the generic requestId-suffixed error text, since a rate limit isn't the kind of failure a requestId helps debug.

**Where it lives in the codebase.** `src/app/dashboard/DashboardInteractive.tsx`'s `errorToast()` function (module-level, shared by the create/edit/delete/list-fetch error paths).

**Interview answer.** Rather than adding a `requestId` prop to `Toast` for one caller's need, the requestId gets composed directly into `detail`, which is already a `ReactNode` and therefore already supports arbitrary content — no design-system file changes required. The requestId matters because it correlates directly to a specific line in clickscope-api's Pino logs, so a user reporting "link creation failed" with that ref string turns a vague bug report into a specific log lookup.

### Types hand-written today, generated in Phase 14

**What it is.** `src/types/api.ts` is a hand-written TypeScript file describing every clickscope-api request/response/error shape this app calls, written by reading the API's route and service source directly — the same approach `src/types/link.ts` already used for `Link` in 12a.

**Why it exists in this project.** The two repos share no OpenAPI spec or types package, so nothing in `api.ts` is checked against the actual running API — it only reflects the contract as of whenever someone last read the source. If `clickscope-api`'s `linkService.ts` serializer adds a field next sprint, this file drifts silently: TypeScript has no way to know, because there's nothing connecting the two. Phase 14's planned OpenAPI spec should *generate* this file instead of it being hand-written — a generated client turns the type checker itself into the drift detector (codegen fails or produces a visible diff the moment the two repos disagree) rather than the disagreement only surfacing at runtime as an unexpected 400 or a field that's silently `undefined`.

**Where it lives in the codebase.** `src/types/api.ts` (this phase's new file, following `src/types/link.ts`'s precedent).

**Interview answer.** Hand-writing `src/types/api.ts` was the only option available in this phase — there's no OpenAPI spec yet to generate from — but it's worth naming as a known limitation rather than a permanent choice: nothing here is checked against the live API, so the two repos can silently drift apart, and a generated client (once Phase 14 ships an OpenAPI spec) would turn that silent drift into a build-time failure instead.

## Phase 13b: Frontend Testing

### RTL's user-facing queries vs. implementation detail

**What it is.** React Testing Library's query priority pushes tests toward `getByRole`, `getByLabelText`, and `getByText` — queries that ask "what would a user, or assistive tech, actually perceive here" — over `container.querySelector(".cs-input")` or reaching into component internals.

**Why it exists in this project.** Every design-system primitive already carries the accessibility wiring this relies on: `Input` (`src/components/design-system/forms/Input.tsx`) associates its `<label>` to the `<input>` via a real `htmlFor`/`id` pair (`useId()`-generated when no `id` prop is passed), `Modal` (`src/components/design-system/feedback/Modal.tsx`) sets `role="dialog"` + `aria-modal="true"` + `aria-label` from its `title`, and `Toast` sets `role="status"`. Querying through those — `getByLabelText("Custom alias")`, `getByRole("dialog").getByRole("button", { name: "Create link" })`, `getByRole("status")` — means a test only breaks when the thing a user would notice actually changes, not when an internal class name or DOM nesting is refactored. The alternative, querying by `cs-*` class names, would tie every test to the exact CSS architecture Phase 12a chose, for zero user-facing benefit.

**How it works mechanically.** Every component test file in this phase (`CreateLinkModal.test.tsx`, `EditLinkModal.test.tsx`, `AuthContext.test.tsx`'s harness, `DashboardInteractive.errorToast.test.tsx`) queries exclusively through `getByLabelText`/`getByRole`/`queryByLabelText` — never a class selector.

**Where it lives in the codebase.** `src/components/patterns/CreateLinkModal.test.tsx`, `src/components/patterns/EditLinkModal.test.tsx`.

**Common pitfalls.** `Input`'s `prefix` prop (e.g. `prefix="short.link/"`) renders as a visually-fused sibling `<span>`, not part of the `<label>` text — so `getByLabelText("Short link")` still matches on just the label's own text, not "short.link/Short link". Worth confirming once by reading the component rather than assuming.

### userEvent vs. fireEvent

**What it is.** `fireEvent.change(input, { target: { value: "x" } })` dispatches one synthetic event with the final value already set. `userEvent.type(input, "x")` simulates each keypress in sequence — `keydown`, `keypress`, `input`, `keyup` per character — the same event sequence a real user's keyboard produces.

**Why it exists in this project.** `Input` is a fully controlled component (`src/components/design-system/forms/Input.tsx` spreads `...rest`, including `value`/`onChange`, straight onto the native `<input>` with no internal value state of its own). `fireEvent.change` would prove the DOM node *can* hold a value; it wouldn't prove the component's `onChange` wiring actually drives that value through React state on every keystroke the way a real user's typing does. `CreateLinkModal.test.tsx`'s "updates the destination URL input as the user types, via real keystrokes" test uses `userEvent.type` specifically so a broken `onChange` (or a `value` prop with no `onChange`, see the standing "controlled inputs" entry above) would actually fail it.

**Where it lives in the codebase.** `src/components/patterns/CreateLinkModal.test.tsx`.

**Common pitfalls.** `userEvent.type` needs `await` — it's async under the hood (real timers between keystrokes by default) — and needs `userEvent.setup()` called once per test, not reused globally, or click/type calls in later tests can interact with stale internal state from an earlier test's setup instance.

### MSW vs. mocking lib/api.ts directly

**What it is.** `msw/node`'s `setupServer` intercepts at the network layer — `src/lib/api.ts`'s real `request()` function runs unmodified, including its own header construction, and only the HTTP response it receives is faked.

**Why it exists in this project.** A `vi.mock("@/lib/api")` stub replaces the exported functions themselves, so nothing inside `request()` ever executes — direct mocking would have skipped past exactly the five behaviors in `api.ts` most worth testing:

1. The `res.status === 204` short-circuit (`api.ts` lines 70-72) that returns `undefined` *before* any `res.json()` call — a mocked `deleteLink` just resolves to whatever the test hands it, proving nothing about that branch existing or running first.
2. That `ApiError.code`/`message`/`requestId` are actually parsed out of the `{ error: {...} }` JSON envelope, not just present on some object a test constructed by hand.
3. The 429 path's two-source `retryAfterSeconds` resolution — `body.error.details.retryAfterSeconds` tried first, the `Retry-After` header as fallback (`api.ts` lines 76-81) — two real branches a mock has no reason to exercise unless the mock itself reimplements the same logic, which defeats the point.
4. The missing-`NEXT_PUBLIC_API_URL` console-error fallback — a module-load-time property of the real file (`BASE_URL` is a top-level `const`), invisible to any mock of `api.ts`'s exports, which is why `src/lib/api.env.test.ts` uses `vi.resetModules()` + a fresh dynamic `import("./api")` instead.
5. That an aborted `AbortSignal` actually propagates through a real `fetch()` call and rejects as `DOMException("AbortError")` — a mocked function has no `fetch` to abort in the first place.

**How it works mechanically.** `src/test/msw/handlers.ts` defines one handler per `lib/api.ts` endpoint against `TEST_API_URL` (`http://localhost:3000`, matching `vitest.config.ts`'s `test.env.NEXT_PUBLIC_API_URL` exactly — a mismatch here means every request silently fails to match, not a passing test). `src/test/setup.ts` calls `server.listen({ onUnhandledRequest: "error" })`, a deliberate strictness choice: an unmocked request is a test bug (a missing handler, a URL typo), not something to let fall through to a real network call. Individual tests override with `server.use(...)` for a specific status code, delay, or header.

**Where it lives in the codebase.** `src/test/msw/handlers.ts`, `src/test/msw/server.ts`, `src/test/setup.ts`; consumed by every test file that imports `server` from `@/test/msw/server`.

**Common pitfalls.** Forgetting `server.resetHandlers()` in `afterEach` (already wired in `src/test/setup.ts`) would let one test's `server.use()` override leak into the next test file's cases, since MSW's handler stack is process-global for the test run.

### The alias-field-absence test as a regression guard tied to a product decision

**What it is.** `EditLinkModal.test.tsx`'s first test asserts `screen.queryByLabelText("Custom alias")` is `null` — not that some other field exists, specifically that this one doesn't.

**Why it exists in this project.** `EditLinkModal`'s own docblock (`src/components/patterns/EditLinkModal.tsx`, lines 19-20) states the short code — and by extension the alias that generated it — is immutable after creation: "changing it would break every copy already handed out." `CreateLinkModal` visibly has a "Custom alias" field right next to fields `EditLinkModal` does share (destination, expiration, password protection), which makes "just add the same field to Edit" a plausible, easy-looking future change for someone who hasn't read that docblock — and one the API's own `UpdateLinkRequest` type explicitly forbids (`src/types/api.ts`, lines 74-77: "NEVER include `customAlias` or `shortCode` — the API's update schema is strict and 400s on any unrecognized key"). `queryByLabelText` (not `getByLabelText`, which would throw before the assertion even ran) returning `null`, checked with an explicit `toBeNull()`, is what makes this test fail the moment that field is added rather than passing vacuously either way.

**How it works mechanically.** Verified live in this phase's mutation-testing pass (mutation `a`, below): adding the field back in made this exact test fail with the exact diff (`expected <input>… to be null`) it's designed to produce.

**Where it lives in the codebase.** `src/components/patterns/EditLinkModal.test.tsx`.

**Common pitfalls.** A test guarding an *absence* is easy to write vacuously (e.g. asserting on an unrelated field and calling it done). The thing that makes this one real is pairing it with the by-hand mutation that reintroduces the field and confirming the assertion — not just the test file — actually goes red.

### Mutation testing applied to the frontend

**What it is.** The same by-hand methodology `clickscope-api`'s Phase 13a used: introduce one specific, plausible regression at a time, on a scratch (uncommitted) edit, run the targeted test file, record the exact assertion that failed (or didn't), then revert before the next one.

**Why it exists in this project.** A test suite that's never been shown capable of failing is unverified by construction — passing tests prove nothing on their own. Four mutations were chosen to each target one specific claim this phase's tests make: a product decision (alias immutability), a precedence rule (`deriveLinkStatus`'s branch order), and two `AuthContext` behaviors (abort-safety, fragment scrubbing).

**How it works mechanically.** The full result, all four run and reverted in this session:

### Why the E2E click flow is async, and what toPass buys over a fixed sleep

**What it is.** `e2e/click-flow.spec.ts` visits the created short link's redirect URL from a second browser context, then polls the dashboard (via `expect(async () => {...}).toPass(...)`, reloading on each attempt) until the click count updates, rather than asserting immediately or after a fixed delay.

**Why it exists in this project.** Per `clickscope-api`'s Phase 9 ("Background Jobs"), the redirect route enqueues a BullMQ job (`enqueueClick`, `src/queues/clickQueue.ts`) instead of writing the click row on the request path; a separate `worker/` process (`worker/processors/clickProcessor.ts`) performs the actual Postgres write, communicating with the API only through Redis. That means the moment the visitor's redirect request completes, the click has **not yet** landed in the database — there's a real, variable-length gap (queue latency plus worker processing time) before a dashboard refetch would see it. A fixed `page.waitForTimeout(N)` would have to guess that gap's upper bound: too short and the test is flaky under any worker slowdown; padded safely long and every run wastes wall-clock time waiting past the moment the job actually finished, for no added correctness.

**How it works mechanically.** `expect(async () => { await page.reload(); await expect(clicksCell).toHaveText("1"); }).toPass({ timeout: 20_000, intervals: [500, 1000, 2000] })` re-runs the entire callback — reload included, since a stale DOM node would never observe a change no matter how long it's polled — on a backoff schedule until the inner assertion passes or the outer timeout elapses. This converges on the actual completion time from either direction: fast when the worker is fast, still correct (not flaky) when it's briefly slower.

**Where it lives in the codebase.** `e2e/click-flow.spec.ts`.

**Production considerations.** This test was run against the real stack in this session (Postgres + Redis via the existing `docker compose up -d` containers, `npm run dev` and `npm run worker:dev` in `clickscope-api`, this repo's own dev server autostarted by `playwright.config.ts`'s `webServer`) and passed in 1.6s — the queue/worker round trip in local dev is fast enough that the very first `toPass` attempt succeeded, no visible retry needed. That's a property of local dev latency, not a guarantee `toPass` relies on; the mechanism is correct regardless of how many attempts it actually takes.

### E2E setup requirements and the Phase 15 CI gap

**What it is.** `e2e/click-flow.spec.ts` requires four live processes: `clickscope-api`'s Postgres + Redis (`docker compose up -d` in that repo), the API itself (`npm run dev`), its worker (`npm run worker:dev`), and this repo's dev server (autostarted by `playwright.config.ts`'s `webServer`, reusing one already running via `reuseExistingServer`).

**Why it exists in this project.** The test exercises the real signup → create-link → redirect → queue → worker → stats round trip on purpose (see above) — no MSW, no mocked worker. That's the entire point of having exactly one E2E test alongside an otherwise-mocked unit/component suite, but it means the test cannot run in isolation the way `npm test` can.

**Where it lives in the codebase.** `playwright.config.ts` (this repo), `docker-compose.yml`/`package.json`'s `dev`/`worker:dev` scripts (`clickscope-api`).

**Production considerations.** Neither repo has any CI configuration today. Wiring this test into CI (Phase 15, per this repo's own convention of naming forward-looking gaps rather than solving them early) will need, at minimum: a Postgres + Redis service in the CI runner (or the existing `docker-compose.yml`, reused), running `clickscope-api`'s migrations before the API starts, starting the API and worker as background processes the CI job can also tear down, and only then starting this repo's own `npm run test:e2e`. None of that infrastructure exists yet — this section documents the requirement, not a solution.

### What's not worth testing here, and why

**What it is.** Three deliberate boundaries on this phase's scope, named explicitly rather than left as silent gaps:

- The generic design-system primitives (`Input`, `Button`, `Modal`, `Toast` — `src/components/design-system/`) have no dedicated unit test files. They're thin wrappers that spread props onto native elements with no logic of their own beyond that; every one of them is already exercised indirectly through every pattern-component test that renders them (`CreateLinkModal.test.tsx` exercises `Input`'s controlled-value wiring and `Button`'s `loading`/`disabled` combination; `EditLinkModal.test.tsx` exercises `Modal`'s dialog role and `Button`'s `saving`-prop-driven disable). A standalone `Input.test.tsx` would just re-assert "a controlled input reflects its value prop," which is React's own contract, not this app's.
- `googleAuthUrl()` (`src/lib/api.ts`) is a pure string template — `` `${BASE_URL}/api/auth/google` `` — not a `fetch` call; it doesn't touch MSW, error parsing, or any of the behaviors this phase's `api.ts` tests target, so it's out of scope here rather than overlooked.
- `Pagination` and `DeleteConfirmModal` (`src/components/patterns/`) have no tests this phase. They weren't named in this phase's explicit scope, and neither backs a specific product decision or precedence rule the way the alias-absence guard does — a plausible next addition, not a current gap.

**Why it exists in this project.** Coverage-for-its-own-sake pulls effort toward whatever's cheapest to test next, not toward what's actually at risk of a real regression — the same argument `clickscope-api`'s Phase 13a made about chasing a coverage percentage up. Every test this phase added targets something with an actual, statable failure mode: a precedence rule, an error-parsing branch, a product decision, an async state-clearing bug. Primitives, a string template, and untouched patterns don't have one of those to point to yet.

## Phase 14b: Generated Types

### Generating `src/types/api.ts` from clickscope-api's committed OpenAPI spec

**What it is.** `src/types/api.ts` and `src/types/link.ts` no longer declare any object shapes by hand. `src/types/generated/api.ts` is the direct, unedited output of `openapi-typescript` run against `../clickscope-api/openapi.json` (regenerate via `npm run types:generate`); `api.ts`/`link.ts` are now a thin alias layer over it — every export is `components["schemas"][...]` or a `paths[...]` index into the generated file, with one deliberate exception (`ApiErrorCode`, see below).

**Why it exists in this project.** Phase 12b named this file's drift risk explicitly (see "Types hand-written today, generated in Phase 14," above): nothing checked `api.ts` against the running API, so a backend field change would drift silently until a request 400ed or a field came back `undefined`. clickscope-api's Phase 14a shipped a committed, generated `openapi.json`, closing the *backend's* spec-vs-code drift risk but explicitly leaving frontend consumer-side drift as a named follow-up (see that repo's "The response-schema drift risk, and its sibling-repo analogue"). This phase closes that loop: the type checker is now the drift detector — if the spec's shape changes, the aliases in `api.ts` fail to compile instead of the two repos silently disagreeing.

**How it works mechanically.** `openapi-typescript` reads the spec file directly (no server needed, works offline and in CI) and emits `paths`/`components` interfaces with zero runtime code. Because the spec has no reusable `$ref` schemas for response/request *wrapper* shapes (`AuthResponse`, `LinkResponse`, etc. are defined inline per-path) and no `operationId` on any operation, `api.ts` can't use a friendly `operations["name"]` map and instead indexes `paths["/exact/path"]["method"]["responses"]["code"]["content"]["application/json"]` literally. Since `requestBody` is typed as optional at the wrapper level (even though every endpoint that has one requires it at runtime), request-shape aliases wrap it in `NonNullable<...>` before indexing into `.content["application/json"]`.

**Where it lives in the codebase.** `src/types/generated/api.ts` (generated, do not hand-edit — header banner and `package.json`'s `types:generate` script both say so), `src/types/api.ts` and `src/types/link.ts` (thin alias layers), `src/lib/api.ts` and its six consumers (`AuthContext.tsx`, `DashboardInteractive.tsx`, `CreateLinkModal.tsx`, `LoginForm.tsx`, `SignupForm.tsx`, `src/test/msw/handlers.ts`) — none of which changed a single import path or identifier, since the alias layer kept the same names at the same `@/types/api` / `@/types/link` locations.

### Diff analysis: hand-written vs. generated

Read the full OpenAPI spec directly and compared every schema/path against the previous hand-written `api.ts`/`link.ts` before touching any application code. Six findings:

1. **Naming only, not real drift.** Hand-written `ApiUser` vs. the spec's `AuthUser` — structurally identical (`id`, `email`, `emailVerified`, `createdAt`, `updatedAt`, all required). Resolved by aliasing `ApiUser` to `components["schemas"]["AuthUser"]`, keeping the name every consumer already used.
2. **The one real drift.** Hand-written `ApiErrorCode` was a closed union of 8 literals (`BAD_REQUEST | UNAUTHORIZED | FORBIDDEN | NOT_FOUND | GONE | CONFLICT | TOO_MANY_REQUESTS | INTERNAL_ERROR`). The spec's `ErrorEnvelope.error.code` is a bare `"type": "string"` with **no `enum`** — clickscope-api's Zod schema (or its OpenAPI registration) never captured this closed set, so naive codegen would widen `error.code` to plain `string`. That would still compile at `SignupForm.tsx`'s `err.code === "CONFLICT"` (comparing `string` to a literal is legal TypeScript) but silently lose autocomplete and exhaustiveness-checking — a real fidelity loss the spec introduces, not one the hand-written type had. Resolved by keeping `ApiErrorCode` as a manually-declared union (documented as deliberately *not* derived) and having `ApiErrorBody` override the generated `error.code: string` back to it via an `Omit`/intersection.
3. **Not actually a diff.** Expected `ApiErrorBody.error.details` to generate as nullable (the spec marks it `"nullable": true` and omits it from `required`) versus the hand-written `details?: unknown`. It doesn't: because the spec gives `details` no `type` at all, `openapi-typescript` emits `details?: unknown` — identical to the hand-written version, since `unknown` already subsumes `null`. Confirmed by reading the generated output directly rather than assuming from the spec JSON alone.
4. **Confirms the hand-written types were accurate.** `CreateLinkRequest`, `UpdateLinkRequest` (including the "never send `customAlias`/`shortCode`" rule — the spec has `additionalProperties: false` and no such fields), `ListLinksResponse.pagination`, and `Link` (including nullable-but-*required* `expiresAt`/`maxClicks`) are exact structural matches. The Phase 12b drift risk never manifested as a real bug anywhere a reusable schema backed the shape — only where the spec itself is loose (finding 2) or absent (finding 5).
5. **Structural, not a value bug.** No `$ref` components exist for the 5 wrapper shapes; they're inline per-path, and there are no `operationId`s anywhere in the spec — see "How it works mechanically" above for the resulting `paths[...]` indexing this forces.
6. **New, currently-unused generated surface.** `HealthReport`, `/`, `/health`, `/api/auth/google[/callback]`, `/{shortCode}`, `/{shortCode}/unlock` all now have generated types nobody consumes yet. Harmless — the frontend simply doesn't call these endpoints today.

Of these, only finding 2 represents a real latent risk (a comparison that would have silently lost type safety); findings 1, 3, and 6 are harmless or non-issues, and finding 4 is a positive result — evidence the original hand-written types were mostly right, just unverified.

**Common pitfalls.** Regenerating `src/types/generated/api.ts` without recompiling leaves stale types in the editor even though `tsc` would catch real drift on the next build. Forgetting the `ApiErrorCode`/`ApiErrorBody` override (finding 2) would silently widen every error-code comparison in the app to plain `string` on the next regeneration if someone "simplified" `api.ts` by aliasing straight from `components["schemas"]["ErrorEnvelope"]`. The lack of `operationId`s means a future spec change that renames a path (not just a field) breaks the `paths["/old/path"]` string literal at the alias site with a clear compile error — which is the intended failure mode, not a bug.

**Production considerations.** Phase 15's CI needs to run `npm run types:generate` and then `git diff --exit-code src/types/generated/` — failing the build if the committed generated file differs from a fresh regeneration against the committed spec, so drift is caught automatically instead of relying on someone remembering to regenerate. This mirrors clickscope-api's own `tests/openapi/spec.test.ts`, which already guards spec-vs-Zod-schema staleness on the backend side. Even with that check in place, one loop stays open: `openapi.json`'s response schemas are themselves hand-mirrored on the API side (`src/openapi/schemas.ts`, per that repo's Phase 14a notes), not automatically verified against live service return types — so this phase's generated frontend types are exactly as trustworthy as that hand-mirroring, no more. Closing *that* loop would mean generating clickscope-api's response schemas from the same Zod objects that build its actual JSON responses, which is out of scope here.

**Interview answer.** Diffing the generated types against the hand-written ones found six things, and only one was a real bug waiting to happen: the spec types API error codes as a bare `string` because the backend's OpenAPI registration never turned its fixed set of Zod error codes into an enum, so naive codegen would have quietly dropped exhaustiveness-checking on every `err.code === "..."` comparison in the app. Everything else was either a naming-only difference or confirmation that the original hand-written types were already correct — which matters, because it means the Phase 12b drift risk was real in principle but had mostly not yet caused an actual bug; this phase closes it going forward by making a compile failure the way drift surfaces, instead of a runtime 400.

## Phase 15b: Frontend Containerization & CI

### Standalone output, and what it silently drops

**What it is.** `next.config.ts` now sets `output: "standalone"`. `next build` emits `.next/standalone/server.js` plus a pruned `node_modules` — traced from the server bundle's actual module graph, not resolved from `package.json`'s dependency/devDependency split — and, by design, **excludes `.next/static/` and `public/`** from that output directory entirely.

**Why it exists in this project.** A container needs to be self-contained: no `npm install` step, no reliance on a host `node_modules`, one process that boots and serves everything. Plain `next build` + `next start` doesn't give that — `next start` still expects the full project directory, full `node_modules`, and the `next` CLI itself present at runtime. Standalone output is Next's answer to "give me exactly what's needed to run this server, nothing else."

**How it works mechanically.** The exclusion of `.next/static/` and `public/` isn't an oversight — Next assumes a "real" deployment puts a CDN or reverse proxy in front of the standalone server and serves those paths from there directly, never routing static-asset requests through the Node process at all. For a Docker image meant to serve everything itself with no such CDN, both directories have to be copied into the standalone output manually, at exact destination paths: `.next/standalone/.next/static` and `.next/standalone/public`. Confirmed directly, before writing the Dockerfile: a plain `npm run build` locally produced `.next/standalone/server.js` and `.next/standalone/node_modules` (38M, versus the root project's full 530M `node_modules`), but no `.next/standalone/.next/static` or `.next/standalone/public` — exactly the exclusion the docs describe, not a version-specific quirk.

**Where it lives in the codebase.** `next.config.ts` (`output: "standalone"`); `Dockerfile`'s `runtime` stage, three `COPY --from=build` lines — one for `.next/standalone` itself, one for `.next/static`, one for `public`.

**Common pitfalls.** The failure mode this produces is easy to miss because it isn't a crash: the server boots cleanly, `docker build` succeeds, a basic health check on `/` can even return 200 if the route itself has no external asset dependency in its critical path — but every CSS file, client JS chunk, and static image 404s, so the app is up and visibly broken at the same time. `ci.yml`'s `docker-build` job's "Verify static assets are served" step exists specifically to catch this: it greps the served HTML for a real `/_next/static/...` reference and curls that path directly, rather than trusting a 200 on `/` alone. Confirmed this step actually works as a regression guard, not just in theory — the built image correctly served a `/_next/static/chunks/*.css` file with a 200 during manual verification.

**Production considerations.** In a deployment that does put a CDN in front of the app (Vercel's own platform, for instance, or a self-hosted setup with Nginx/Cloudflare in front of the Node process), the "waste" of also serving static assets directly from the Node process inside this image is mostly moot — those requests would be intercepted upstream before ever reaching the container. This image is built to be correct as a fully self-contained unit regardless of what (if anything) sits in front of it in a real deployment, which is out of scope for this phase (Phase 15c).

**Interview answer.** `output: "standalone"` traces the server bundle's real dependency graph and gives you a minimal, self-contained `node_modules` — but it deliberately leaves out static assets, on the assumption a CDN serves those in front of it. A Docker image that has to be fully self-contained needs two extra `COPY` lines to put `.next/static` and `public` back, at exact paths, or you ship a server that boots fine and serves a broken page. I verified this by inspecting the standalone output directly before touching the Dockerfile, and by adding a CI step that actually curls a real static asset path instead of just checking that the server responds at all.

### `NEXT_PUBLIC_*` vars are baked at build time, not read at container runtime

**What it is.** `NEXT_PUBLIC_API_URL` (read in `src/lib/api.ts`) is inlined directly into the client JS bundle by `next build` — it is not looked up from `process.env` when the container starts. The Dockerfile threads it through as a build `ARG`, promoted to `ENV` before `RUN npm run build` in the `build` stage, not as a runtime `ENV`/`docker run -e`.

**Why it exists in this project.** This is the frontend's sharpest divergence from how clickscope-api handles configuration. The API's `DATABASE_URL`/`REDIS_URL`/`SENTRY_DSN` are read once, at process startup, from whatever environment the container is actually running in — the same built image can be pointed at different databases just by changing `-e` flags on `docker run`. `NEXT_PUBLIC_API_URL` cannot work that way: by the time the container exists, the value is already compiled into static `.js` chunks. Passing a different value via `docker run -e NEXT_PUBLIC_API_URL=...` has no effect whatsoever on the already-built bundle — the same image cannot be repointed at a different API without rebuilding it.

**How it works mechanically.** `ARG NEXT_PUBLIC_API_URL` declares the build-time input; `ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL` makes it visible to the `RUN npm run build` step's environment, which is where Next's own build-time env-inlining picks it up and substitutes it into every reference in client-bundled code. Verified directly, not assumed: built the image once with `--build-arg NEXT_PUBLIC_API_URL=http://localhost:3000`, extracted `.next/static` from the running container, and confirmed the literal string appeared in one JS chunk. Rebuilt with `--build-arg NEXT_PUBLIC_API_URL=http://api-changed-value:9999` and confirmed the new value appeared in the bundle and the old one was completely gone — proving the ARG genuinely threads through the build, not that some default elsewhere happened to match.

**Where it lives in the codebase.** `Dockerfile`'s `build` stage (`ARG`/`ENV` pair, before `RUN npm run build`); `src/lib/api.ts` (the only runtime consumer of the resulting inlined value); `ci.yml`'s `docker-build` job (`--build-arg NEXT_PUBLIC_API_URL=http://localhost:3000`, a placeholder sufficient for the smoke test since no live API is reachable in that job — only static serving is being verified there).

**Common pitfalls.** The natural-looking mistake is setting `NEXT_PUBLIC_API_URL` only in the `runtime` stage (or only on `docker run -e`), which builds and runs without error and silently ships a client bundle pointed at whatever value (or no value) was present during the `build` stage instead. Because this fails silently — no crash, no error, just requests going to the wrong host, or a build-time `undefined` baked in as the literal string `"undefined"` — it's exactly the kind of bug that only surfaces once someone notices the deployed app can't reach its API, not during `docker build`.

**Production considerations.** Every real deployment target (a registry push per environment, or a build step in a deploy pipeline) needs to pass the correct, environment-specific `NEXT_PUBLIC_API_URL` at `docker build` time — this is a build-time input to the image, not a runtime configuration of a container. A CD pipeline that treats it like an ordinary runtime secret (injected at deploy time, not build time) would ship every environment with whatever value happened to be present the one time the image was built. Out of scope for this phase (Phase 15c), but the constraint is worth stating now since it shapes how any future build/deploy pipeline has to be structured.

**Interview answer.** `NEXT_PUBLIC_*` variables are compiled into static JS at `next build` time, not read from the environment when the server starts — the opposite of how the backend's env vars work. That means the value has to be a Docker build argument threaded into the build stage's environment before `next build` runs, not a runtime `-e` flag. I proved this rather than assumed it: built the image once, confirmed the value in the served bundle, rebuilt with a different value, and confirmed the bundle actually changed and the old value was gone.

### Docker build as a distinct check from `npm run build`

**What it is.** `ci.yml`'s `docker-build` job actually runs `docker build` and boot-smoke-tests the result, separate from the `test` job's `npm run build`/`npm run typecheck`.

**Why it exists in this project.** clickscope-api's Phase 15a justified the same kind of job with a repo-specific reason: its root `tsconfig.json` excludes `worker/`, so the Docker build's own `tsc` invocation was the *only* place that repo's CI typechecked the worker at all. That specific justification does not carry over here — this repo has one `tsconfig.json` covering the whole tree, and `npm run typecheck` in the `test` job already covers everything the Docker build would also compile. What *does* carry over, in a form specific to this repo's own build model: a passing `next build` proves the app compiles and prerenders correctly, but proves nothing about whether the standalone output's files end up in the right place inside a container, whether the non-root user can actually read them, or whether a build-arg meant to reach the build stage actually got there. Those are Dockerfile/build-pipeline correctness questions, not application-code correctness questions, and only actually building and running the image answers them.

**How it works mechanically.** The job builds the image with a real `--build-arg`, then runs two separate boot-smoke checks: a polling curl against `/login` (proves the container starts and serves HTTP within a bounded window), and a second step that greps the served HTML for a real `/_next/static/...` reference and curls that path directly (proves the static-copy paths from the "Standalone output" section above are actually correct, not just assumed correct because the server responded). Both failure modes — a crash on boot, and a "boots fine but assets are broken" state — are boot-time facts a passing `next build` cannot see.

**Where it lives in the codebase.** `.github/workflows/ci.yml`, `docker-build` job.

**Common pitfalls.** Treating a green `test` job as sufficient signal that the image is deployable would miss exactly the class of bug this job is built to catch — a Dockerfile `COPY` pointed at the wrong path, or a build-arg that silently didn't thread through, neither of which `next build` running outside a container could ever detect.

**Production considerations.** Building the image on every PR (not just on merge) means a broken Dockerfile is caught before merge, in the PR that introduced it, rather than surfacing later during an actual deploy attempt.

**Interview answer.** `next build` and `docker build` verify different things here. `next build` (run in the `test` job) proves the Next.js app itself compiles, typechecks, and prerenders correctly. `docker build` plus a boot-smoke test (run in a separate job) proves the *image* — the specific file layout, the non-root permissions, the build-arg wiring — actually works once packaged and run as a container. A repo with a more unusual tsconfig layout, like clickscope-api's excluded `worker/` directory, might get an additional typecheck-coverage benefit from this job too; here it's purely about Dockerfile/build-pipeline correctness, and that's still worth a dedicated check.

### Why the runtime stage skips `npm ci --omit=dev`

**What it is.** The `Dockerfile`'s `runtime` stage does not run any `npm install`/`npm ci` command at all — it only copies `.next/standalone`, `.next/static`, and `public` from the `build` stage.

**Why it exists in this project.** clickscope-api's `runtime-base` stage runs its own fresh `npm ci --omit=dev` specifically to exclude devDependencies from the shipped image, since that repo's build output is plain compiled JS with no dependency pruning of its own. It would have been easy to copy that pattern here without checking whether it still made sense — this plan explicitly investigated that question instead of assuming the pattern transfers. It doesn't: `output: "standalone"` already performs its own dependency trace at build time, walking the server bundle's actual module graph and copying only the production packages genuinely reachable from it into `.next/standalone/node_modules`. Running `npm ci --omit=dev` in the runtime stage on top of that would be redundant work against a `package.json` this stage doesn't even need, and worse, would resolve a *different*, un-traced dependency set — package-manager dependency resolution, not build-time module tracing — than the one the server bundle was actually built and tested against.

**How it works mechanically.** Confirmed directly: a local `npm run build` produced a `.next/standalone/node_modules` of 38M, versus the project's full `node_modules` at 530M — evidence the trace-based pruning is doing real work on its own, without any `--omit=dev` step involved.

**Where it lives in the codebase.** `Dockerfile`, `runtime` stage — notably, the *absence* of a `RUN npm ci` line where the API's equivalent stage has one, with an inline comment explaining why.

**Common pitfalls.** Copying a working pattern from a sibling repo's Dockerfile without checking whether its underlying assumption still holds is the exact trap this section documents avoiding — the same stage-naming convention (`deps` → `build` → `runtime`) and the same non-root/exec-form-CMD reasoning genuinely do transfer from the API's Dockerfile; the `npm ci --omit=dev` step specifically does not, because it solves a problem `output: "standalone"` already solved differently.

**Production considerations.** None beyond what's already covered — this is purely a build-pipeline correctness point, not a runtime behavior difference.

**Interview answer.** The API's Dockerfile does a fresh `npm ci --omit=dev` in its runtime stage because its build output is plain compiled JS with no dependency pruning built in. I checked whether that same step made sense here before copying it, and it doesn't — `output: "standalone"` already traces the server bundle's real module graph and ships only what's actually reachable from it, which is a more precise form of pruning than a package.json-driven install could produce, and running a second, different dependency resolution on top of it would contradict rather than reinforce that.

### Build success as a Server/Client boundary check

**What it is.** `ci.yml`'s `test` job runs `npm run build` on every PR — the same command Phase 12a's Notes.md already identified as this app's actual enforcement mechanism for the Server/Client component boundary, now running automatically instead of relying on someone remembering to run it locally.

**Why it exists in this project.** This app has real, deliberate structure at that boundary: `layout.tsx` stays a Server Component specifically so `/design-system`'s async `QrCodePopover` can render; `providers.tsx` is a thin, separate `"use client"` file wrapping `AuthProvider`, rather than putting `"use client"` on `layout.tsx` itself, precisely so the rest of the tree under it can stay server-rendered; `DashboardInteractive.tsx` is a client leaf component specifically scoped away from its parent `page.tsx`. A change that violates one of these boundaries — a hook creeping into a file that's supposed to stay a Server Component, a server-only API called from a `"use client"` file — fails at build/render time, not at typecheck, because TypeScript's type system has no concept of "this function can only run on the server."

**How it works mechanically.** `next build`'s prerendering step actually renders every route. A boundary violation surfaces as a build failure with a specific, identifiable error, not a silent runtime bug — confirmed directly this phase: `npm run build` (both locally and inside the Docker `build` stage) reported all six routes (`/`, `/_not-found`, `/dashboard`, `/design-system`, `/login`, `/signup`) as `○ (Static) prerendered as static content`, meaning every one of them rendered successfully with the current Server/Client structure intact.

**Where it lives in the codebase.** `ci.yml`'s `test` job's `npm run build` step; `src/app/layout.tsx`, `src/app/providers.tsx`, `src/app/dashboard/DashboardInteractive.tsx`, `src/app/design-system/page.tsx` (the actual boundary structure this check protects).

**Common pitfalls.** Treating a build failure here as "just a build hiccup" and reflexively adding `"use client"` to make an error go away is the actual risk — that fixes the symptom by converting a Server Component to a Client Component, potentially breaking exactly the thing (like `/design-system`'s async `QrCodePopover`) that depended on it staying server-rendered. The build failure is the correctness signal; the fix should address why the boundary was crossed, not silence the check.

**Production considerations.** This check now runs on every PR instead of depending on a developer remembering to run `npm run build` locally before pushing — closing the gap between "this check exists" and "this check reliably runs."

**Interview answer.** In this app, the client/server boundary isn't enforced by a type — it's enforced by whether `next build` can actually render the tree. Several files here (`layout.tsx`, `providers.tsx`, `DashboardInteractive.tsx`) are deliberately structured around that boundary, and a regression there fails as a build error, not a type error. Making `npm run build` a required CI step turns that from "a check someone has to remember to run" into "a check that always runs."

### The CI-shape problem for E2E

**What it is.** `e2e/click-flow.spec.ts` is not gated on every pull request. It runs on push to `main`, on a nightly `schedule` (06:00 UTC), and on manual `workflow_dispatch` — a narrower trigger set than `ci.yml`'s unit/integration tests, decided deliberately rather than defaulted to "run everything everywhere."

**Why it exists in this project.** This test needs a fundamentally heavier setup than anything else in this repo's CI: a second public repository checked out (`clickscope-api`), Postgres and Redis service containers, that repo's migrations applied, its API process and worker process both booted and confirmed live, and only then this repo's own frontend booted via Playwright's `webServer`. That's multiple minutes of setup before a single assertion runs, and it introduces a real cross-repo coupling risk this repo's PRs don't otherwise have: an unrelated change on `clickscope-api`'s `main` branch — nothing to do with any pending `clickscope-web` PR — could make this workflow fail, purely because it always checks out `clickscope-api`'s current `main`. Gating that on every PR would mean this repo's own PR feedback speed and reliability depend on a second repository's current state, for a check that's fundamentally about cross-repo integration, not about the diff in front of a reviewer. Meanwhile, `ci.yml`'s `test` job already gives fast, fully self-contained PR-time coverage — Vitest against MSW-mocked responses, no external services, no second repo, finishing in seconds.

**How it works mechanically.** `push: branches: [main]` means every merge to `main` gets a real, full-stack run shortly after landing — a much tighter feedback loop than "only nightly" while still being decoupled from individual PRs' review cycles. `schedule: cron: '0 6 * * *'` (06:00 UTC) is a backstop that catches drift even during a period with no merges — for instance, a `clickscope-api` `main` change with no corresponding `clickscope-web` push to trigger the E2E run any other way. `workflow_dispatch` exists for on-demand manual runs, used directly during this phase's own implementation to validate the workflow before waiting for either a merge or the nightly schedule.

**Where it lives in the codebase.** `.github/workflows/e2e.yml`.

**Common pitfalls.** The tempting alternative — run E2E on every PR "to be safe" — trades PR-time speed and reliability for a check that, in this specific setup, is measuring something broader than the PR's own diff (this repo's compatibility with `clickscope-api`'s current `main`), and does so at a real time cost per run. The opposite mistake — no scheduled run at all, only push-to-main — would leave a real gap: a period with no `clickscope-web` merges could still accumulate an undetected `clickscope-api`-side regression indefinitely.

**Production considerations.** How someone notices this workflow silently stopped running: GitHub automatically emails repository watchers (and, by default, whoever's permissions make them eligible for Actions notifications) when a **scheduled** workflow run fails — this requires no extra integration, alerting service, or dashboard to set up. What this does *not* solve: GitHub automatically disables a `schedule`-triggered workflow after 60 days with zero activity on the repository — if the nightly run simply stops appearing in the Actions tab at all (not failing, just absent), the automatic failure-email mechanism above never fires, because there's no failed run to email about. Nothing in this phase's code detects that disablement; it's a known, named gap, not a solved one. A `push`-triggered run landing shortly after every merge to `main` is a second, independent signal in the meantime — an active repo naturally re-triggers the workflow (and implicitly keeps the schedule trigger's 60-day counter from expiring) far more often than the nightly cron alone would.

A concrete, out-of-scope-for-now extension worth naming: an opt-in PR label (e.g. `run-e2e`) that adds a `pull_request` trigger filtered to that label, giving reviewers a lever to request the full E2E run on a specific integration-sensitive PR without paying its cost by default on every PR. Not built in this phase — noted as the natural next step if PR-time confidence in cross-repo behavior becomes a recurring need.

**Interview answer.** E2E here needs a second repository, two service containers, two backend processes, and this repo's own frontend all booted together — a fundamentally different cost profile than this repo's own unit tests. I chose to run it on push-to-main (fast feedback after every merge), a nightly schedule (a backstop against drift during periods with no merges), and manual dispatch (for on-demand validation) — deliberately not on every PR, since that would make this repo's PR feedback speed and reliability depend on a second repository's current state, for a check that's really validating cross-repo integration rather than the PR's own diff. GitHub's automatic failure-email on a failed scheduled run means silent failure isn't actually silent — but I also named the one gap that isn't solved: GitHub disables idle scheduled workflows after 60 days, and nothing here detects that happening.

### Image size: standalone vs. a naive build

**What it is.** Measured directly, not estimated: the standalone-based image built from this phase's `Dockerfile` is **285MB**. A naive single-stage equivalent — `COPY . .`, `npm install` (full dependencies + devDependencies), `npm run build`, `CMD ["npm", "run", "start"]`, built temporarily for this comparison and removed afterward — is **1.35GB**. The multi-stage, standalone-based image is roughly **4.7x smaller**.

**Why it exists in this project.** The naive image ships things the running server never touches: `@playwright/test`, `vitest`, `jsdom`, `msw`, `typescript`, `oxlint`, `openapi-typescript` and their own transitive dependencies (all devDependencies, needed only to build and test the app, never to run it), plus every `.tsx`/`.ts` source file, the `e2e/` directory, and an un-pruned `node_modules` sized to the full monorepo-style dependency tree rather than to what the server bundle actually imports.

**How it works mechanically.** Two things compound: the multi-stage `Dockerfile`'s `runtime` stage starts from a fresh `node:24-alpine` and copies in only `.next/standalone` (which already excludes devDependencies via `output: "standalone"`'s own build-time trace — see "Why the runtime stage skips `npm ci --omit=dev`," above), `.next/static`, and `public` — no source files, no `e2e/`, no full `node_modules` ever enter the final image at all. `.dockerignore` also excludes `node_modules`, `.next`, `e2e/`, test artifacts, and repo docs from the build *context* itself in both cases, meaning even the naive comparison image (which still installs everything fresh inside the container) never had a chance to accidentally `COPY` a stale local `node_modules` or `.git` history from the host — the 1.35GB figure already reflects a reasonably careful naive build, not a worst-case one with no `.dockerignore` at all.

**Where it lives in the codebase.** `Dockerfile` (the actual multi-stage build); `.dockerignore`.

**Common pitfalls.** It's tempting to assume `output: "standalone"` alone accounts for most of the size difference, but the multi-stage structure matters just as much: even with standalone output, a single-stage Dockerfile that never discards the `build` stage's full `node_modules`, source tree, and build tooling would still ship most of that weight — the size win comes from the runtime stage starting fresh and copying in only the three traced/pruned artifacts, not from `output: "standalone"` in isolation.

**Production considerations.** Smaller images mean faster registry pushes/pulls and faster cold starts on any platform that has to fetch the image before running it — a real, if not this phase's primary, concern once this image is actually deployed (Phase 15c).

**Interview answer.** Measured, not estimated: 285MB for the multi-stage standalone build versus 1.35GB for a naive single-stage equivalent — about 4.7x smaller. The difference comes from two things working together: `output: "standalone"` traces the server bundle's real dependencies instead of shipping the whole installed tree, and the multi-stage Dockerfile's runtime stage starts fresh and copies in only that traced output, so none of the build tooling, devDependencies, or source files that were necessary to *build* the app ever end up in the image that *runs* it.

### What changes for a team project with a real release cadence

**What it is.** This phase's CI/CD setup is scoped to one contributor and one deploy target (none yet — deployment itself is Phase 15c). A few things named here as deliberately out of scope, worth reconsidering if this becomes a team project with regular releases and multiple contributors:

- **PR-opt-in E2E via label.** The `run-e2e` label idea named in "The CI-shape problem for E2E" above becomes more valuable with more contributors and more PRs in flight simultaneously — giving reviewers a lever to request full cross-repo validation on a specific PR without changing the default trigger set for everyone.
- **Docker layer caching across CI runs.** Neither `ci.yml` nor `e2e.yml` currently caches Docker layers between runs (matching clickscope-api's own Phase 15a choice not to) — each `docker build` in CI starts cold. A registry-based cache (`--cache-from`/`--cache-to` against a pushed cache image) or `actions/cache` with BuildKit's cache export would speed up CI as build frequency increases.
- **Required status checks.** Branch protection on `main` making `ci.yml`'s jobs (and, once release-gated, `e2e.yml`) required-to-pass-before-merge checks — currently nothing blocks a merge on CI failure; the workflows run and report, but don't gate.
- **Pinning the checked-out `clickscope-api` ref.** `e2e.yml` currently always checks out `clickscope-api`'s `main` branch. In a team setting with independent release cadences per repo, pinning to a specific tag or commit SHA (bumped deliberately, as its own reviewable change) would stop an unrelated backend change from breaking this repo's E2E run without warning — trading "always tests against the latest backend" for "tests against a backend version this repo has explicitly signed off on."
- **Image vulnerability scanning.** Neither this phase nor the API's Phase 15a runs a scanner (e.g. Trivy, Grype, or GitHub's own Dependabot/code-scanning image support) against the built image — worth adding once images are actually pushed to a registry and deployed.
- **Semantic image tagging and a real registry push.** Images are currently built and smoke-tested but never pushed anywhere or tagged beyond `:ci`/`:local` — a real release cadence needs a registry, a tagging scheme (commit SHA, semver, or both), and a defined promotion path from a passing CI build to a deployed image. Out of scope here; this is exactly what Phase 15c covers.
