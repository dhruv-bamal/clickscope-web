# Notes

## Phase 12a: Design System Integration

### Server Components vs. Client Components

**What it is.** Next.js's App Router renders every component as one of two kinds. A Server Component runs only on the server: it can be `async`, it can read files or query databases directly, and its output is serialized into the React Server Component (RSC) payload — a compact description of the tree, not JavaScript. A Client Component is marked with a `"use client"` directive at the top of its file; it hydrates in the browser, can hold state, and can attach real event listeners to DOM nodes. Every file in this project is a Server Component by default unless it opts into `"use client"`.

**Why it exists in this project.** Phase 12a's entire component-conversion pass (task 4 of the plan) hinges on getting this classification right for 25 exports across 24 files. Get it wrong in one direction and you ship a fully client-rendered app with no benefit from the App Router at all; get it wrong in the other and the build fails outright with an RSC boundary error. There is no partial credit — `npm run build` either succeeds or names the exact line that crossed a boundary it shouldn't have.

**How it works mechanically.** A Server Component categorically cannot: call a React hook (`useState`, `useEffect`, `useId`, `useContext` — none of them; the RSC renderer doesn't implement a hooks dispatcher for them), touch a browser-only API (`window`, `document`, `localStorage`), or attach a live event handler to a native DOM element in a way that survives serialization — a function value has no representation in the RSC payload, so `<button onClick={fn}>` rendered from a pure Server Component tree fails at build/render time with "Event handlers cannot be passed to Client Component props." What it *can* do that a Client Component can't: be `async` and `await` directly in the component body, which this phase uses for real — `QrCodePopover` and its inner `QrGlyph` are `async function` Server Components that `await QRCode.toString(shortUrl, { type: "svg" })` and stream the resulting SVG down as markup, with zero client JavaScript involved in generating it.

**Where it lives in the codebase.** The per-component classification is the table in the initial plan for this phase (25 exports; 5 need `"use client"`, 20 don't) and is re-derived, file by file, in `src/components/design-system/`. `src/components/design-system/feedback/QrCodePopover.tsx` is the concrete async-Server-Component example — and it's the reason `src/app/design-system/page.tsx` (the showcase) is *not* one big `"use client"` file despite being an internal dev-only page that would otherwise have no reason to split boundaries. It was written that way at first, and it broke immediately: React DevTools' console flagged `<QrCodePopover>` and its inner `<QrGlyph>` with "is an async Client Component. Only Server Components can be async at the moment," the instant the page tried to render QrCodePopover from inside a `"use client"` tree. The fix was the split now in place — `page.tsx` stays a Server Component and renders `<QrCodePopover>` directly, `src/app/design-system/ShowcaseInteractive.tsx` is the one `"use client"` boundary holding every other demo's state, and `src/app/design-system/Section.tsx` is a small hooks-free wrapper both files import. That's a stronger demonstration of "boundaries are contagious downward, not upward" than a clean build would have been: it's not just that the *other* 20 components don't need `"use client"` — it's that one of them (QrCodePopover) actively *cannot* tolerate being pulled into a client boundary it doesn't need, and the page has to be shaped around that.

**Common pitfalls.** Two, both actually hit by this phase, not hypothetical. First: `src/components/patterns/EditLinkModal.tsx` originally synced its local form state from `initialValues` inside a `useEffect` — a Client Component, so it compiled fine, but it's still wrong, and oxlint's `react/set-state-in-effect` rule caught it immediately (`npx oxlint --import-plugin src`). Calling `setState` synchronously inside an effect schedules a second, redundant render; the fix was to initialize state directly from props on mount and document a `key`-based remount contract for callers that need to reset the form when the target link changes, rather than reacting to a prop change after the fact. Second, the one described above: rendering an async Server Component from inside a `"use client"` tree fails at runtime, not build time — `npm run build` and `npm run lint` both passed cleanly with the bug in place; only opening the page in a browser and reading the console surfaced it, which is the concrete reason this phase's own plan called for using the feature in a browser rather than trusting the build alone.

**Production considerations.** The build is the enforcement mechanism, not a linter: get a boundary wrong and `npm run build` fails with a specific, named error rather than silently degrading. That's a stronger guarantee than most architectural conventions get, but it also means the failure mode is a full build break, not a warning — worth running `npm run build` after any component-library change, not just `npm run dev`, since dev mode is more forgiving about some boundary violations that only surface under production compilation.

**Interview answer.** Server Components run once on the server and serialize to a compact payload; they can't hold state, use hooks, or attach live event handlers, because none of that survives being flattened into a description of a tree. Client Components hydrate in the browser and can do all of that, at the cost of shipping JavaScript. Next.js defaults every file to a Server Component; you opt a file into the client with `"use client"` only when it actually needs interactivity. Getting the boundary wrong isn't a style nit — it's a build error, because a function handler or a hook call has no valid representation once it's serialized into the RSC payload.

### `"use client"` is a boundary, not a file marker — the Icon case

**What it is.** `"use client"` doesn't mean "this file uses React"; it means "this file is the seam where the client module graph begins." Everything that file imports and renders directly — every component in *its* module graph that doesn't have its own `"use client"` — gets pulled into the client JavaScript bundle too. But that pull only runs *downward*, into what the Client Component imports. It does not run *upward*, into whatever imports the Client Component. A Server Component can import and render a dozen different Client Components as children without becoming one itself, because each of those is a separate, self-contained boundary — the Server Component just describes where they go in the tree and hands them their props.

**Why it exists in this project.** Before this phase, `docs/design/components/icon/Icon.jsx` was the one component actively fighting this model: it used `useEffect` + `useRef` to imperatively inject `<i data-lucide="name">` into the DOM and then called the CDN global `window.lucide.createIcons()` to hydrate it into an SVG. Real hooks, a real browser-only global — Icon genuinely needed `"use client"`, no way around it. And Icon is imported by essentially every other component in the library (`Button`, `Badge`, `LinkCard`, `Toast`, `IconButton`, `EmptyState`, `StatCard`, `DataTable`'s cell renderers, and on) — it's the single most-imported module in the whole bundle. The naive, *wrong* conclusion from that fact is "Icon needs `use client`, so everything that renders `<Icon>` needs it too" — treating the directive as contagious upward. It isn't. A component that renders `<Icon name="copy" />` and has no hooks or browser APIs of its own stays a perfectly valid Server Component regardless of what Icon itself is; Icon becomes its own small client boundary nested inside an otherwise server-rendered tree, and the parent never needs the directive at all.

**How it works mechanically.** This phase rewrote `Icon.tsx` (`src/components/design-system/icon/Icon.tsx`) to resolve icon names through a static, eager `Record<string, LucideIcon>` map built from `lucide-react`'s named exports — no `useEffect`, no `useRef`, no CDN global, no hooks at all. That makes Icon itself a plain, pure, fully server-renderable function component. The real, measurable effect isn't that 20 *other* components stopped needing `"use client"` because of Icon — under the correct downward-only model, they never needed it on Icon's account in the first place. The effect is that the temptation to over-mark them evaporates, and each of the 25 exports in the library can be judged purely on *its own* hooks/browser-API usage, with no Icon-shaped asterisk. That per-component audit is what actually produced the count: 20 of 25 exports need nothing; the other 5 (`Modal`, `AnalyticsChart`, `Input`, `Textarea`, `Select`) need `"use client"` for reasons that have nothing to do with Icon — `Modal` for its own `useEffect`+`window.addEventListener` Escape-key handling, and `AnalyticsChart`/`Input`/`Textarea`/`Select` for their own `useId()` calls (a hook, and therefore just as unavailable to a Server Component as `useState` — this one is easy to miss, since `useId` doesn't *look* stateful the way `useState` does, but the RSC renderer doesn't special-case it).

**Where it lives in the codebase.** `src/components/design-system/icon/Icon.tsx` (the rewrite itself); the client/server classification table in this phase's plan lists all 25 exports with a one-line reason each; `src/components/design-system/feedback/Modal.tsx`, `src/components/design-system/data-display/AnalyticsChart.tsx`, and the three `forms/{Input,Textarea,Select}.tsx` files each carry a top-of-file comment naming their specific hook, not a generic "needs use client" note — the specificity matters, because it's what makes each classification independently verifiable rather than copied down a list.

**Common pitfalls.** Assuming `"use client"` propagates upward through the import graph — it doesn't, and designing a component library as if it does leads to marking dozens of presentational leaf components client-only for no reason, which quietly reintroduces the client-bundle bloat Server Components exist to avoid. The opposite mistake is just as real: components that merely *forward* an `onClick`/`onChange` prop via `{...rest}` (`Button`, `IconButton`, `Checkbox`, and others) don't need `"use client"` themselves — but the moment some ancestor actually attaches a real function to that prop, a client boundary needs to exist *somewhere* between the data-fetching Server Component and that DOM element. This phase ships no such wiring yet (no data fetching, no real handlers — that's 12b), so it's untested by this phase's own build; 12b is where a wrong assumption here would first surface as a real error.

**Production considerations.** Every additional `"use client"` boundary is JavaScript the browser has to download, parse, and hydrate. A design-system library that marks its leaf primitives client-only "just in case" pays that cost on every page that imports any of them, even pages that render those components in a fully static context. Keeping the boundary at the smallest possible unit — one hook-bearing component, not its entire subtree of importers — is a real, compounding performance decision, not a stylistic one.

**Interview answer.** `"use client"` marks a boundary, and boundaries only pull things in one direction: into the client bundle go the file itself and everything *it* imports and renders directly, but nothing upstream of it is affected. Icon originally needed the directive because it used `useEffect`, `useRef`, and a browser-only CDN global to inject SVGs imperatively; since it's imported by nearly every other component in the library, it would be easy to conclude the whole library needed to go client-side. That conclusion is wrong — a Server Component can render a Client Component as a child and stay a Server Component itself. Rewriting Icon to a static, hook-free lookup over `lucide-react` made Icon itself server-safe, which matters less for what it directly fixed and more for removing the reason anyone would've reached for the wrong mental model in the first place. The actual audit, done per-component and independent of Icon, found 5 of 25 exports need `"use client"` — each for a hook or browser API that's genuinely its own.

### Token architecture: plain CSS custom properties, not Tailwind

**What it is.** The design-system bundle ships its visual language as CSS custom properties — `--color-primary`, `--space-4`, `--radius-lg`, and so on — defined once in `tokens/*.css` and consumed via `var(--token-name)` everywhere, including inline `style={{ padding: "var(--space-4)" }}` objects throughout the reference screens. Every component class (`cs-btn`, `cs-card`, `cs-modal`, …) is hand-written BEM-like CSS in `css/components.css` that reads those same variables. This project ported that system into `src/styles/design-system/` unchanged in structure, imported once from `src/app/globals.css`.

**Why it exists in this project.** The bundle's own `uploads/design_v2.md` spec is written *as* a Tailwind v4 `@theme` document — but the actual shipped CSS in `docs/design/css/` and `docs/design/tokens/` doesn't use Tailwind at all. Grepping both files for `@tailwind`/`@apply` returns zero hits. That's not an oversight to correct; it's the real, load-bearing authoring convention of every file in the bundle, and every reference screen in `docs/design/ui_kits/` lays out with inline `style={{ ... }}` objects referencing the same custom properties rather than utility classes. Adding Tailwind to this project would mean introducing a second, parallel styling system with zero existing components to migrate onto it, a build-time cost, and a convention that matches nothing already here — pure overhead with no components it would actually simplify.

**How it works mechanically.** `src/styles/design-system/index.css` is a pure `@import` manifest (fonts → tokens → base → components, same order as the source bundle's `styles.css`), imported exactly once from `src/app/globals.css`, which `layout.tsx` imports exactly once. One deviation from the source, made deliberately: `tokens/fonts.css`'s Google Fonts CDN `@import` for Geist/Geist Mono was dropped in favor of `next/font/google`, which Next.js's own `create-next-app` scaffold already wires into `layout.tsx` — it self-hosts both font files at build time and exposes them as `--font-geist-sans`/`--font-geist-mono` on `<html>`. `tokens/typography.css`'s `--font-sans`/`--font-mono` now resolve those variables first, falling back to the literal family names. Same tokens, same visual result, one less external network dependency — and it resolves the second half of the bundle's own readme caveat ("Geist/Lucide loaded from CDN rather than vendored"), the Lucide half being what the Icon rewrite already fixed.

**Where it lives in the codebase.** `src/styles/design-system/tokens/{colors,typography,spacing}.css`, `src/styles/design-system/css/{base,components}.css`, `src/styles/design-system/index.css` (the manifest), `src/app/globals.css` (the one-line entry point), `src/app/layout.tsx` (the `next/font` wiring).

**Common pitfalls.** Reaching for a utility class that doesn't exist because there's no Tailwind config generating one — every visual value in this project comes from an explicit token or an inline `style` object, never a `p-4`/`bg-slate-100`-style class. The oxlint adherence config's raw-hex/raw-px/raw-font-family bans were meant to catch exactly the failure mode of someone hand-writing a value instead of reaching for a token — see the "what the bundle gave and didn't give" section below for why that specific enforcement mechanism doesn't currently run.

**Production considerations.** Because every component already consumes tokens via `var()` rather than any build-time class generation, there's no purge/JIT step to configure and no risk of a class being tree-shaken away because a linter didn't detect it in a dynamic string. The tradeoff is the inverse of Tailwind's: verbose inline `style` objects instead of terse utility classes, in exchange for zero build tooling and a token system that's just... CSS, legible without a mental compile step.

**Interview answer.** The source bundle's spec document describes a Tailwind v4 `@theme` design, but the CSS it actually ships is 100% hand-written custom properties consumed via `var()`, with zero Tailwind directives anywhere — confirmed by grep, not assumption. Every reference screen lays out with inline styles referencing those same variables. Given that, adding Tailwind to this project would mean running two styling systems side by side with nothing to migrate onto the new one — pure cost, no benefit. So this phase ported the token system as-is, with one real improvement: swapping the source's CDN-loaded Geist fonts for `next/font/google`, which Next.js already wires up, self-hosting the fonts and removing an external network dependency without changing a single visual token.

### Deriving view state from domain facts

**What it is.** `deriveLinkStatus()` (`src/lib/deriveLinkStatus.ts`) is one pure function that maps five independent domain booleans/values from the API's `Link` resource — `isActive`, `expiresAt`, `maxClicks`, `clickCount`, `isPasswordProtected` — onto the design system's single, mutually-exclusive `status` enum (`active | expiring | expired | protected | paused`) that `Badge` and `LinkCard` already expect.

**Why it exists in this project.** `clickscope-api` has no `status` field on `Link` at all — it was never a design goal there. What it does have, in `src/routes/redirect.ts`'s `deadStateError()`, is a priority-ordered check for whether a link is *dead*: inactive wins first, then a past `expiresAt`, then an exhausted `maxClicks`, all three collapsing to the same 410 Gone response. That function exists for a redirect handler's narrow purpose (should this request be served or not) and was never meant to produce a five-value UI enum. The frontend needs its own mapping, but it needs to encode the *same underlying precedence logic* the API already committed to, or the two would silently disagree about what "dead" means. The trickiest fact this function has to get right, and the reason it can't just read `isActive` naively: `worker/processors/linkCleanupProcessor.ts`'s scheduled sweep only flips `is_active = false` for links dead by *expiry* — never for links dead by exhausted `maxClicks` — and it runs on a delay. So a click-capped link can sit with `isActive: true` in the database indefinitely, and a time-expired link can sit with `isActive: true` for a window after it expires but before the sweep runs. Reading `isActive` at face value would show "Active" for links that are, functionally, already dead.

**How it works mechanically.** Five ordered rules, most severe first: (1) `expired` if `expiresAt` has passed *or* `clickCount >= maxClicks` — checked before `isActive`, specifically so an unswept, click-capped-or-past-expiry link shows "Expired" rather than the misleading "Active"; (2) `paused` if `isActive` is false and rule 1 didn't already fire — this is what correctly isolates a genuine manual deactivation from an unswept natural expiry, since the expiry/cap check already ran first; (3) `protected` if `isPasswordProtected` and the link isn't within the expiring-soon window; (4) `expiring` if `expiresAt` is within 3 days — chosen as the threshold on the reasoning that it's wide enough to be useful without being so early it becomes noise, and it wins over `protected` when both are true, since time pressure is actionable in a way a static password setting isn't; (5) `active` otherwise. All three of these — the 3-day window, click-cap counting as expired, and expiring-over-protected precedence — are product decisions with no single objectively correct answer; they were made explicitly rather than defaulted into silently, which is the entire point of writing them down here instead of letting them fall out of whichever screen happened to need a status first.

**Where it lives in the codebase.** `src/lib/deriveLinkStatus.ts` (the function and its inline precedence comments); `src/types/link.ts` (the hand-written `Link` interface it types against — hand-written because `clickscope-api` and `clickscope-web` share no types package or OpenAPI spec, so this is the one place that shape gets asserted on the frontend and has to be kept in sync by hand); `clickscope-api/src/routes/redirect.ts`'s `deadStateError()` and `clickscope-api/worker/processors/linkCleanupProcessor.ts`'s `sweepExpiredLinks` (the API-side precedent this function's ordering is built to stay consistent with).

**Common pitfalls.** Computing status inline in a component from `link.isActive ? "active" : "paused"` — the single most tempting shortcut, and exactly what produces the "unswept link shows Active" bug described above. Anywhere this function's logic gets duplicated instead of imported, the list view and the detail view are one edge case away from disagreeing about the same link's status, and neither call site would have any signal that they'd drifted.

**Production considerations.** One function is the whole point here, not a stylistic preference: every consumer — the link list, the detail header, a future email digest or Slack notification — must apply identical precedence, and a single source of truth is the only way a future change to, say, the expiring-soon window doesn't require hunting down every place that logic got copied.

**Interview answer.** The API has no `status` field — it has five independent facts, and its own redirect handler already estabishes a priority order for treating a link as dead (inactive, then expired, then click-capped) for its own narrow purpose. `deriveLinkStatus()` is one pure function that reuses that same precedence to produce the UI's single status enum, and it specifically checks expiry and click-cap *before* `isActive`, because the API's cleanup worker only sweeps expired links on a delay and never sweeps click-capped ones at all — so a dead link can sit with `isActive: true` for a while, and reading that flag naively would show it as live. Three product decisions (the 3-day expiring window, click-cap counting as expired, and expiring beating protected when both are true) got made explicitly and surfaced rather than picked silently, and it's one function specifically so every screen that shows a status agrees with every other one.

### What the handoff bundle gave and didn't give

**What it is.** `docs/design/` is a complete, internally consistent design-system handoff: CSS tokens, a Geist type system, 24 React components each with a paired `.jsx` implementation, `.d.ts` prop contract, and `.prompt.md` usage doc, four full-screen reference UI kits, and an oxlint "adherence" config meant to enforce the whole thing at lint time. Its own readme calls it "complete and validated," with two caveats: no real logo, and Geist/Lucide loaded from CDN rather than vendored.

**Why it exists in this project.** Knowing precisely where the bundle's authority ends matters more than restating what it covers well — everything past that line is a decision this phase had to make (and in several cases, explicitly ask about) rather than one the bundle made for it.

**How it works mechanically — what it gave.** All 24 components port cleanly with their `.d.ts` folded in as real TypeScript interfaces (`src/components/design-system/`). The token system, base reset, and component CSS are complete enough to need zero new visual decisions for anything the bundle already modeled. `Modal.prompt.md` documents the destructive-confirm pattern precisely enough that `DeleteConfirmModal` (`src/components/patterns/DeleteConfirmModal.tsx`) is a direct instantiation of it, not an invention. The reference `SignInScreen`/`AuthCard` layout in `docs/design/ui_kits/` was faithful enough to mirror exactly for the new `SignupForm` (`src/components/patterns/SignupForm.tsx`) — centered card, icon-in-circle header, OAuth button + divider, `cs-card` body — with no new layout invented, just new fields.

**What it didn't give.** No `package.json`, no `lucide-react` (Icon was CDN-only — the rewrite this phase's whole first half is built around). No pagination component or pattern anywhere, despite the API's `GET /api/links` returning exactly the offset/limit/total/hasMore shape a Prev/Next control needs (`src/components/patterns/Pagination.tsx` is new). No signup screen — only a dead `href="#"` stub inside the reference `SignInScreen`, and no `name` field to collect even if there were, since `clickscope-api`'s `users` table has none (`migrations/20260810111606772_create-users-table.ts`). No `max-clicks` input anywhere, in *any* form, despite the API fully supporting the field — `EditLinkModal` adds one as a plain `Input`, matching the user's explicit call on that gap. A `QrCodePopover` whose glyph is explicitly commented `/* Deterministic visual QR glyph (NOT scannable) */` — replaced with `qrcode`'s real SVG renderer, `await`-ed inside an async Server Component. A `Tag` component and an ad-hoc tags column in the reference `LinksScreen`, for a field (`tags`) that doesn't exist anywhere in the API's schema — confirmed via a repo-wide grep, zero hits — so nothing in this phase's ported components or new patterns wires a tags field to anything. And an oxlint adherence config written against ESLint's `no-restricted-syntax` rule, which the installed oxlint version (1.79) doesn't implement at all — `oxlint -c _adherence.oxlintrc.json` fails outright with "Rule 'no-restricted-syntax' not found in plugin 'eslint'." Its `no-restricted-imports` half works and was kept (with the path globs fixed to this project's real `@/components/design-system/*/**` alias); its 41 per-component prop-contract selectors were dropped rather than resurrected, both because they can't run under this oxlint version and because — even setting that aside — they'd be redundant with TypeScript now that every component is a real `.tsx` file with a real interface, and actively wrong for the six components (`Button`, `IconButton`, `Input`, `Textarea`, `Select`, `Checkbox`) that spread `{...rest}` onto a native element and extend React's own `*HTMLAttributes<...>`: the generated allowlists only included each component's own custom props, so they'd have flagged ordinary, correct usage like `<Input type="email" onChange={...} />` as a violation. Full reasoning in `.oxlintrc.json`'s header comment.

**Where it lives in the codebase.** Everything above traces to a specific file already named in this section — that specificity is deliberate, so this note stays checkable against the code rather than becoming stale prose.

**Common pitfalls.** Assuming "complete and validated" in the bundle's own readme means complete for *this* product — it means complete relative to the visual spec it was built against, which never modeled auth screens, pagination, or a max-clicks input in the first place, and separately never got test-run against the actual lint tool this project uses. Both are worth checking explicitly rather than inheriting the bundle's own confidence in itself.

**Production considerations.** None of this phase's four new patterns (`SignupForm`, `DeleteConfirmModal`, `EditLinkModal`, `Pagination`) or the QR/oxlint fixes required inventing new visual language — every one of them composes existing tokens and existing components, or (for oxlint) removes rules that can't run rather than replacing them with something new. That constraint held throughout specifically so 12b's API-wiring work inherits a design surface with zero pending "which one is real" ambiguity.

**Interview answer.** The bundle is genuinely complete for what it set out to model — tokens, 24 components, four reference screens — but "complete" has a boundary, and this phase's job was finding it precisely rather than assuming it. Concretely: no npm dependencies at all (Icon's CDN dependency was the big one), no pagination, no signup screen, no max-clicks input despite the API supporting the field, a QR code that explicitly isn't scannable, a `Tag` component built for a field the API schema doesn't have, and an adherence lint config written against a rule (`no-restricted-syntax`) the actual installed linter doesn't implement. Every gap got a specific fix traced to a specific file, and every new piece reused existing components and tokens rather than inventing new ones — the four new patterns and the QR/oxlint fixes are compositions of what already existed, not new design decisions.
